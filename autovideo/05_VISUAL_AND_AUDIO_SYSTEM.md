# 05｜视觉与声音系统 v0.2（设计修订）

## 1. 什么是高质量

高质量不是素材数量或特效密度，而是四层体验共同成立：

1. **理解**：观众看见的变化确实解释了旁白，不只是同步出现一行文字。
2. **感知**：观众能迅速辨认当前主体、关系、变化、结果。
3. **视听**：字体、布局、运动、语音、音乐、音效组成统一风格与自然节奏。
4. **工程**：没有切断旁白、乱码、越界、意外静帧、错位和丢失媒体。

前三层无法仅靠 Schema 测试保证；第四层应尽可能自动化。

## 2. 创作语法：对象 → 状态 → 动作 → 结果

视频不是一叠页，而是**画面状态随时间改变**。

- **Object（对象）**：发送者、信道、数据包、对照方案、数值等。必须可辨识。
- **State（状态）**：对象当前位于何处、是否有效、是否被选中、显示何种数值。
- **Beat（动作）**：出现、传输、高亮、改变、受损、比较等受控变化。
- **Result（结果）**：观众在这个动作后应该明确看见的变化。

每个主镜头包含 `visual_intent` 和 1 个及以上 `beats`。不强制每几秒出现特效；静止有时对理解更好，但无意义长时间不变化必须在评审中被识别。

### 样例：通信噪声

| 旁白段 | 视觉对象 | 动作 | 应当被看见的结果 |
|---|---|---|---|
| “发送者通过信道传递信息” | 两端与通道 | 渐入、激活路径 | 信息正在从左到右传播 |
| “但噪声会干扰信号” | 通道与数据 | 标记通道被干扰 | 数据传输可能受影响 |
| “接收的内容可能不同” | 发送值与接收值 | 并置、突出不相同 | 观众一眼看到差异 |

第一版若没有一个组件能同时实现所有动作，**应使用多个连贯镜头组合**，而非在同一个场景里混入不受支持的自由代码。

## 3. 设计系统：唯一默认主题 `minimal_dark`

下面是**起始设计 token（需要样片测试后校准）**，不是业界统一最佳值：

| token | 建议值 | 用途 |
|---|---|---|
| 画布 | 1920×1080，30fps | 固定输出 |
| 背景 | `#0B1020` | 深色画面 |
| 主要文字 | `#F2F5FA` | 主要说明 |
| 次要文字 | `#B2C0D4` | 辅助标注 |
| 主强调色 | `#4DB6E8` | 主要流、选中态 |
| 警示强调 | `#F3AC64` | 干扰、差异 |
| 内容安全区 | 左右 120px，上 90px，下方保留字幕区 | 防止电视/移动端裁切及拥挤 |
| 标题字号 | 建议 64–88px | 允许内容自适应 |
| 正文/节点标签 | 建议 38–52px | 以真实 1080p 抽帧检验 |
| 字幕 | 建议 42–54px，最多 2 行 | 汉字、中英混排、标点都需实测 |

字体必须采用项目可分发的**合法授权**字体并等待字体加载后再测量排版；仅限制字数不足以保证不溢出。涉及视频音乐、音效也须明确授权来源；不随交付包分发字体原始文件。

视觉布局采用以下分工：**主舞台**表达概念、关系或变化；**旁白字幕区**只辅助理解，不占用主视觉主体。不要让字幕覆盖图表关键数据。标题卡/内容镜头的文字视觉层级必须区分。

## 4. 时间与运动语言

每个 Beat 的视觉呈现分为：

- **建立**：明确出现了什么对象。
- **作用**：对象如何变化，重点发生了什么。
- **停留**：给观众理解结果的时间。
- **交接**：自然结束或衔接到下一个镜头。

运动曲线、时长和节奏由组件设计系统统一控制。避免所有组件都使用相同的生硬线性移动；也避免无意义弹跳、过度模糊、随机粒子和闪烁。

组件应提供有限的 motion profile（例如 `standard`, `subtle`）供设计系统选择，而不是让 LLM 自由指定 easing 函数、像素坐标和每帧数值。确实需要特殊运动时，新增组件动作并单独测试。

## 5. 六个主组件不是六种静态页面

| 组件 | 适用内容 | 示例可用动作 | 重要视觉限制 |
|---|---|---|---|
| `title_card` | 主题建立 | reveal / emphasize / hide | 不堆叠长段落 |
| `concept_reveal` | 定义、属性、解释点 | reveal / highlight / hide | 同屏内容数量受控 |
| `flow_diagram` | 因果、流程、信号路径 | reveal / highlight / activate_path / mark_disrupted | 有方向、节点语义和合法路径 |
| `comparison` | 方案对比、状态差异 | reveal / highlight / emphasize_difference | 对照单位一致，不用动画伪造差异 |
| `timeline` | 时间顺序、阶段演变 | reveal / highlight | 先后关系必须准确 |
| `bar_chart` | 数量比较 | reveal / highlight | 单位、数值与轴清楚，禁止误导性基线 |

动作名是**语义协议**；组件可以内部使用 SVG/Canvas/CSS/Remotion 等实现，渲染器不得向模型开放底层代码。

每个组件交付必须包含：

1. props Schema 和 targets/action registry；
2. 固定种子与固定输入的静态示例；
3. 至少一个**包含 2 个可观察 Beat 的动效测试**；
4. 正常文字长度及超长中文、中文数字、英文缩写等边界样例；
5. 生成前、中、后关键帧，以及渲染失败时明确错误。

## 6. 不做 PPT 的最小验收

对任一声称有内容表达的镜头，检查：

- 视觉意图是什么？是否能找到镜头中的具体对象承载该意图？
- 是否至少有一次**有意义的状态变化**，或有明确理由保持静止？
- 在变化发生后，观众能否直接读到结果，而不仅听到旁白？
- 去掉旁白后，画面是否仍保留一部分解释信息？（设计评议的启发式，不作为机械硬门槛。）

对于一整段 60 秒视频，不能全部是标题卡 + 每页整段文字进出场；自动报告要标注此风险，人类样片评议据此评定视觉解释力。

## 7. 声音生产与混音策略

### 旁白

- 实际 TTS 先生成，再将音频交给音时标对齐器；优先获取真正的词/短语边界。
- 声音验收关注自然度、中文多音字、数字单位、专名与停顿；不可只凭 provider 返回 200 判断可用。
- 同一条视频默认一个声音与一套发音风格；必要时允许针对数字/缩写修正 TTS 文本，但字幕仍显示适合阅读的文本。

### 背景音乐和音效

- V0.1 **不要求 AI 自动创作音乐**，优先使用已授权、可合法分发的素材；允许无音乐。
- 背景音乐始终弱于人声；如需动态 ducking，使用确定性规则，在旁白区间自动压低音乐。
- 音效应绑定到被声明的 beat，不让渲染器任意随机放置效果；`audio_mix` 中的音量值必须限幅。
- 可从 -16 LUFS 附近作为整片响度的**试验基线**开始，但最终应按试听及发布场景确认；同时监测峰值、异常静音、音轨错位。

### 字幕

- SRT 与烧录字幕来自同一份、以真实语音为依据的分段时间线；不可维护两套独立文稿。
- 当只有句/短语时间戳时，只做相应粒度的字幕；不虚构逐字“卡点”。
- 字幕布局须按**中文分词与视觉宽度**控制断行，不能直接照搬依赖英语空格分词的字幕分页算法。
- 字幕是统一 overlay，不由每个主场景自行排版；不得挡住节点、曲线和数字。

## 8. 双轨 QA

**机械门槛（硬门）**：真实音视频流、字幕一致性、无非法引用/越界、无渲染错误、无音频截断、字体加载、可解码、动作真的在指定帧发生。

**视听表达门槛（研发评审）**：视觉意图清楚、动作有解释价值、整体节奏连贯、画面具辨识度、旁白舒服。多模态 LLM 可以提出诊断，但不等于客观审美真值。

关键帧采样不能只取场景首中末；**每个 beat 都要采样前、触发点附近、状态完成后的帧**，验证“画面确实发生了预期变化”。

## 9. G1 的最低证明

给定 10–20 秒真实授权音频 fixture 和合法 Video IR，要求一个 `flow_diagram` 镜头至少能：先展示发送和接收端，再激活可观察的信号路径，并根据下一句出现干扰状态。保存三个以上对应该 Beat 的关键帧，并提供固定时间帧的可复现测试。

这项测试比“成功输出 MP4”更能说明视觉系统不是简单 PPT 模板。
