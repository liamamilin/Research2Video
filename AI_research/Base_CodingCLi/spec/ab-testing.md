# A/B 测试：独立模块设计

状态：设计已定（2026-11-04），尚未开发。

## 1. 要解决什么

开头、封面、标题、片头这类改动，现在只能做前后对比。可前后两段时间的话题、时段、热点都不一样，看到的变化分不清是改动带来的，还是这些差异带来的。A/B 测试的做法是：在同一段时间里，把自动出片的 job 随机分成两组，A 组照现状，B 组用改动，然后由程序按事先定好的规则比较两组。

用户的使用流程：

1. 打开「A/B 测试」tab，创建一个对比实验：改什么、A 是什么、B 是什么、看哪个指标、在哪些矩阵或栏目上跑。
2. 开始以后，自动出片的 job 按比例随机分到 A 组或 B 组，照常发布。
3. 过一段时间，tab 里自动显示数据，到终点后给出结论。
4. 用户决定要不要把改动应用到正式工作流。

## 2. 原则：独立模块，对现有应用零影响

A/B 测试是现有后台里的一个**独立模块**：跑在同一个后台进程里，用同一套登录，在同一个界面里占一个 tab；有自己的代码目录、自己的数据库、自己的分析和实验定义。不单独部署成另一个服务：单独的服务要多维护一套启动和监控，两边通信本身还会出错，而它照样要读现有数据库，得不到额外的隔离。它对现有应用只做两件事：

- **读**：只读现有应用的稿件、发布记录和 B站数据。
- **回答一个问题**：现有应用建稿时问「这份稿件在不在实验里、在哪一组」，A/B 模块回答 A 或 B，B 组同时给出要用的设置。

对现有应用的保护：

| 保护 | 做法 |
| --- | --- |
| 只有一个写入点，只问不改 | 现有应用只在建稿处加一次调用，把回答写进这份稿件冻结的 `content_context`。另有几处只读展示（§2 边界规则 1 的白名单）。A/B 模块不写现有应用的任何表和配置 |
| 任何异常都按 A 处理 | A/B 模块出错、数据库忙或打不开、被关闭或者没装，回答都是 A，也就是和现在完全一样 |
| 一键关闭 | 总开关关掉后，接入点永远回答 A；正在进行的实验暂停分组，已有的数据保留 |
| 只能改登记过的开关 | B 的设置只能用开关登记表里的开关（§6），开始前要先通过栏目配置原有的校验 |
| B 组的改动失败了就退回现有做法 | 比如封面文字没生成出来，就照旧用标题封面，同时记一笔「这条没生效」 |
| 限制分流范围 | 只有自动生产的 job 参加，手动选题不参加；每个实验自己设 B 组的比例 |
| 不改正式配置 | 「采用」只生成一份建议改动，由用户在现有的配置页面里确认、保存（§10） |

**没有正在进行的实验，或者 A/B 模块关着的时候，现有应用的行为和今天完全一样。** 这一条要写成测试。

### 边界规则

1. **代码边界**：A/B 的代码只放在 `core/experiments/`、`web/routes/experiments.py` 和界面的「A/B 测试」tab 里。现有代码对 A/B 模块的引用只有下面这份白名单：
   - **写入点（唯一）**：建稿处调用 `experiments.arm_for(...)`（§5）。
   - **启动**：`web/server.py` 启动时调用一行 `experiments.start_background()`，由 A/B 模块自己开线程做定时检查：到终点停止分组、SRM 报警、建议止损、排队的实验自动开始、对账（§11）。不往现有的 `autopilot_loop` 里加调用。
   - **只读展示**：首页提醒、稿件详情和出片列表上的「实验 X · B 组」、每周复盘的「实验进展」和 B 组标记、配置页的预填改动和「来自实验 X」、助手读取实验记录。这些地方只读稿件自己的 `content_context.experiments`，或者调用 A/B 模块提供的只读函数；A/B 模块出错、缺失时就不显示这一块，原有功能照常。
   - 白名单以外，现有代码不引用 A/B 模块的任何东西。
2. **依赖单向**：A/B 模块可以通过现有的只读接口读现有数据。现有代码不依赖 A/B 模块：A/B 模块缺失、导入失败或报错时，现有代码照常运行。
3. **数据分开**：A/B 用自己的 `state/experiments.db`，不写现有的表。唯一例外是建稿时，把分组结果写进这份稿件自己的 `content_context`。
4. **出错隔离**：`arm_for` 由调用方包一层：异常、数据库忙、总开关关闭，一律当作 A。进程内的 sqlite 调用没法可靠地按 1 秒截断，所以不设单独的超时，而是用 sqlite 自带的忙等超时（`timeout=2`，等锁超过 2 秒就抛错），再由外层的异常保护接住，按 A 处理。
5. **用测试守边界**：
   - 测试一：没有实验时，建出的稿件和现在逐字段一致。
   - 测试二：A/B 模块抛异常或导入失败时，建稿照常完成。
   - 测试三：扫描代码，现有代码里引用 `core.experiments` 的地方都在白名单里（边界规则 1）。
   - 测试四：A/B 模块的只读函数全部抛异常时，白名单里的每个展示点照常返回，只是少了实验那一块。
6. **能整个拿掉**：删掉 A/B 目录和白名单里的调用，系统就回到现在的样子。

## 3. 为什么是「主账号随机分流」

| 方案 | 结论 |
| --- | --- |
| 同一条视频放两个版本 | B站没有这个功能（没找到多封面测试；YouTube 的 Test & Compare 是在同一条视频里做的） |
| 主账号同时发 A、B 两版 | 同一个号里内容重复，两条会抢同一批观众，还可能触发查重，不作为常规手段 |
| 两个测试账号交叉发布 | 没有两个测试账号（用户 11-04 确认） |
| **主账号随机分流** | **采用**。每个 job 只出一个版本，不多花成本，不重复发布，样本来自真实流量 |

分流下两组的题材和内容不一样，处理办法：

- **随机分组**：分到哪组和题材无关，好题材不会集中在某一组，题材造成的只是随机波动，不会形成系统性偏差。
- **分层**：每个栏目内按出片顺序轮流分到 A、B，分析时按「栏目 + 周」比较（§7、§8）。
- **只在差距超过「题材本身能造成的差距」时才认定改动生效**（§8）。用最近的视频做 A/A 模拟（什么都不改，只随机分两组），单靠题材就能拉出的差距（90% 的情况落在这个范围内）如下：

| 每组视频数 | 3 秒退出 | 完播率 |
| --- | --- | --- |
| 20 条 | ±19 个点 | ±12 个点 |
| 50 条 | ±13 个点 | ±7 个点 |
| 110 条 | ±9.5 个点 | ±5 个点 |

（2026-11-04 的数据，3 秒退出只有 68 条视频有，50、110 条两行是有放回抽样估出来的。）

这套方法做不到三件事：

- 不能判断某一条视频是不是因为改动才好，只能看两组的平均效果。
- 改动只对部分题材有用时，效果会被平均掉。
- 小改动测不出来，只适合测大的改动，比如开头整个换掉、封面换样式。

## 4. 开源方案调研

| 项目 | 许可 | 结论 |
| --- | --- | --- |
| [GrowthBook](https://docs.growthbook.io/faq) | 核心 MIT | **不集成**，借鉴思路。它是为网站用户流量设计的：要单独部署服务和数据库，分析要对接数据仓库。我们的分组单位是视频，数据在 SQLite 里。借鉴的是哈希分组、实验定义、护栏指标和 SRM 检查 |
| [gbstats](https://pypi.org/project/gbstats) | MIT | **不用**。最新的 0.8.0 是 2024-06 发布的，要求 `pandas<2`、`numpy<2`，和我们的 pandas 2.3.1 冲突 |
| [PostHog](https://vwo.com/blog/open-source-ab-testing-tools/) | MIT | **不集成**。需要 ClickHouse 等一整套服务，而且按用户事件设计 |
| Unleash / Flagsmith / Flipt / FeatBit（[对比](https://toolradar.com/compare/flipt-vs-growthbook)） | 开源 | **不集成**。只管功能开关，不做分析 |
| [spotify-confidence](https://github.com/spotify/confidence) | Apache 2.0 | **不用**。依赖 statsmodels、chartify、ipywidgets，用的是大样本正态近似，不适合每组几十条的规模 |

结论：自己写，统计部分用分层置换检验和自助法，纯 Python 实现，不新增依赖。

## 5. 结构

```
现有应用（不变，除了一处）                     A/B 测试模块（新，独立）
─────────────────────────                     ──────────────────────────────
建稿 video_workflow.start                     state/experiments.db          实验定义（草稿和正式）
   │  ① 问：这份稿件在哪一组？ ───────────────▶  同一个库                       分组、事件、结果
   │  ② 收到 A，或者 B 加设置    ◀───────────────  分组：分层随机（§7）
   │     （异常、数据库忙、关闭一律当 A）
   ▼
写入这份稿件冻结的 content_context
（B：覆盖登记过的开关，并记下 experiments）
   │
写稿 → 出片 → 封面 → 发布（照常，从 content_context 读设置）
   │
publications（bvid ↔ script_id）    ─── 只读 ──▶  取数据：按 script_id 找到 bvid
B站采集（快照、创作中心数据）          ─── 只读 ──▶  分析引擎（纯函数）→ 结论
                                                │
                                                ▼
                                   「A/B 测试」tab：创建、进度、结论、建议改动
```

接入点放在**建稿那一刻**，具体位置是 `video_workflow.start` 里、`content_guard.new_topic` 之后、`store.create_script` 之前，因为 `content_context` 在这里冻结，写稿、出片、封面都读这一份（[content_columns.snapshot](../core/video/content_columns.py)）。B 组只要在这里改一次，整条视频就从头到尾按 B 走，写稿类、画面类、封面类的改动都能测。现有应用的其他代码不用为「实验」做任何改变。读取新开关的那几处（§6）是正常的功能开发，没有实验时按默认值走，和今天一样。

## 6. 开关登记表

B 组只能改登记过的开关。每个开关登记五项：写进 `content_context` 的哪个位置、由哪一步读取、允许什么取值、默认值（等于现状），以及**读取时机**：「写稿前」（研究、选题、去重时就会读到）还是「写稿起」（写稿或之后才读）。读取时机决定失败怎么算（§8）。

| 开关 | 写入位置 | 由谁读 | 读取时机 | 现状 |
| --- | --- | --- | --- | --- |
| `greeting` | `content_context.greeting` | 写稿（问候语） | 写稿起 | 已有 |
| `notes` | `content_context.notes` | 写稿（创作方向）；**研究和选题也读**（`research_dossier`） | 写稿前 | 已有 |
| `presentation.strategy` | `content_context.presentation` | 出片（画面讲述方向） | 写稿起 | 已有 |
| `render.*` | `content_context.render` | 出片参数 | 写稿起 | 已有 |
| `greeting_position` | `content_context.greeting_position` | 写稿 | 写稿起 | **要新增**，默认 `before` |
| `opening_card` | `content_context.presentation.opening_card` | 出片（AutoVideo） | 写稿起 | **要新增**，默认关 |
| `cover_style` | `content_context.cover_style` | `publish_covers` | 写稿起 | **要新增**，默认数字封面 |
| `packaging.intro` | `content_context.render.packaging` | 出片 | 写稿起 | 待确认现有配置能否单独关掉片头 |

读取时机要开发时用代码核对（搜索读取这个字段的地方），不能只凭名字判断。

要新增的开关，属于现有应用的正常功能，随第一个用到它的实验一起开发。没有实验时取默认值，行为不变。

## 7. 分组

- **时机**：只在建稿时分组。实验开始前建的稿件不参加；重写新版本、重新出片都沿用原来的组。
- **资格**：分组仍在建稿时做，但只有「走到写稿那一步」的稿件才计入分析和 SRM。原因：去重不在建稿时，而在后台运行里、研究之后（`story_pool.take`）。11-04 核对：10-28 以来自动稿件失败 91 条，去重没选题 44 条，联网搜索不可用 43 条，其他 4 条，都发生在建稿之后，建稿时没法知道。
  - 实验只改「写稿起」的开关时，写稿之前的失败和分到哪组无关，两组都排除，不算缺失。
  - 实验改了「写稿前」的开关（比如 `notes`）时，B 组可能因此更容易被去重拦下，所以写稿前的失败也要照旧算作缺失（意向处理），不能排除。
  - 写稿之后的失败、下架、删除，一律算缺失（§8）。
  - 掉稿是随机的，会打乱分块的均衡，靠分析时的「栏目 + 周」分层来补。
- **范围**：只看实验 `scope` 匹配的、自动生产的稿件。
- **栏目内轮流分组**：每个栏目一天只出 1–2 条，按天切层的话，很多层里只有 1 条，没法分。所以分组时不按天切，在每个栏目内按出片顺序分块：比例 50% 时每 2 条一块，块内随机一条进 A、一条进 B；比例 30% 时每 10 条一块，块内随机 3 条进 B。这样每个栏目里两组的数量始终接近设定比例。
- **可复现**：块内的随机排列取自 `sha256(实验id:栏目:块序号)`，结果同时写进库里，以库里为准。
- **并发**：自动建稿只在后台进程的 `autopilot_loop` 里跑，有文件锁 `autopilot-tick` 串行化；但手动建稿也会调用 `arm_for`（它会回答「不参加」），A/B 模块自己的定时线程也会读写 `experiments.db`。所以读块计数、分组、写入仍放在同一个 `BEGIN IMMEDIATE` 事务里完成，代价很小。拿不到锁时按 §2 的忙等超时处理（按 A，不计入实验）。
- **分组号**：稿件 id 在 `store.create_script` 里才生成，而接入点在它之前，所以 `arm_for` 先发一个分组号（token），和组别一起写进 `content_context.experiments`，比如 `{"id": "...", "arm": "B", "token": "..."}`。A/B 模块的定时线程只读扫描 scripts 表，按 token 把分组和稿件对上。分了组、建稿却失败的分组号，对账时丢掉，不计入实验，也不计入 SRM。
- **重试不重新分组**：自动出片重试时用的是已有稿件（`video_autopilot` 里的 `existing or video_executor.create(...)`），不会再走建稿，所以不会重新分组。要有测试守住这一点。
- **进行中锁定**：实验开始后，开关、取值、范围、主要指标、终点都锁定，只能暂停或结束。要改就复制成一个新实验。
- **冲突**：两个正在进行的实验，范围有重叠时，不能改同一个开关。改不同开关的实验可以同时跑，即使看同一个主要指标：两个实验各自随机分组，互不造成偏差。同一条稿件可以同时在两个实验里，`content_context.experiments` 是列表。
- **记录代码版本**：每次分组时记下当前代码的 git 提交号。实验期间代码有变化，tab 里会提示；被测开关相关的代码改过时，提示「比较可能不公平」。
- **SRM 检查**：用二项检验看两组样本数是否偏离设定比例，p < 0.01 就报警。出现这种情况，通常是某一组的稿件在流程中途掉了，比如写稿失败或被去重拦下，这时实验结论不可信。

## 8. 取数据与分析

**计入**：已经发布到 B站、能通过 `publications` 找到 bvid 的稿件。分到哪组就算哪组（意向处理）。分母按 §7「资格」：只改「写稿起」开关的实验，从走到写稿的稿件算起；改了「写稿前」开关的实验，从建稿算起。分母里写稿失败、被去重拦下、在 B站下架或删除的稿件，都算缺失，同时计入 SRM 检查。缺失也要分组列出：某一组缺失明显更多，本身就说明改动有问题（比如 B 组更容易写稿失败）。指标还没出来的算「待测」。

**同龄读取**：每个指标取「发布满 48 小时后第一次读到的值」，不取最近一次的值，保证 A、B 两组的视频是在相同年龄被读取的。24 小时播放照旧从快照插值得出。

**数据覆盖**：3 秒退出和封面点击只对进了创作中心诊断列表（最近约 50 条）的视频才有。11-04 核对：10-28 到 11-01 自动发布的 30 条里，完播率和平均观看时长 30 条都有，3 秒退出和封面点击只有 24 条（80%）。规则：

- 某个指标缺数据的视频，不计入这个指标的分析，在 tab 里分组列出缺了几条。
- 两组的缺失比例相差超过 15 个点时报警「数据缺失不均，结论不可信」，因为缺失可能和改动有关。
- 默认主要指标用完播率（覆盖完整）。只有改动明确针对开头时，才用 3 秒退出做主要指标。
- 以后如果想让覆盖完整，在现有采集里补上逐条读取。这是现有功能的改进，不是 A/B 模块去写现有数据。

**指标**：3 秒退出、封面点击超过同类、完播率、平均观看时长、24 小时播放，全部来自现有的每日采集，A/B 模块只读。主要指标从前三个比率类里选（默认完播率，见上面的数据覆盖），播放量容易被一条爆款带偏，只作护栏指标。

**只用主要指标下结论**：同时看很多指标，总会有一个碰巧显著。所以结论只看事先定好的那一个主要指标；护栏指标只能否决结论；其他指标只展示，标明「仅供参考」。

**检验**：
- 每组给出样本数、中位数、四分位数。
- 差异的算法：每条视频的指标先减去它所在「栏目 + 周」层的中位数，再把各层合在一起，算 B 组和 A 组的中位数之差。这样题材和栏目的高低被扣掉，只比较层内的相对高低。两组都只有 1 条以下的层跳过不用，记在结果里。
- 区间：分层自助法（在每层内对 A、B 分别有放回抽样，10,000 次，固定随机种子）给出差异的 90% 置信区间。结论只看这一个区间，不另做置换检验。
- 误判率：区间是双侧 90%，所以把没有差别误判成「B 更好」的概率不超过 5%，误判成「有差异」（不分方向）的概率不超过 10%。
- 核对：近两周 100 条自动视频分布在 9 个栏目、16 个「栏目 + 周」层里，89 条落在 4 条以上的层中，分层后丢掉的很少。

**结论规则**（程序判定，按顺序）：

1. 没到终点：「进行中」，只显示数字，**不下结论**，避免中途看数字就提前下判断。
2. SRM 报警：「分组失衡，结论不可信」。
3. B 组实际生效率低于 80%：在结论里注明。
4. 到了终点：
   - 主要指标的区间完全落在「更好」一侧，并且没有护栏指标明显变差：「B 更好」。护栏「明显变差」指区间整个落在「更差」一侧，并且超过阈值：比率类（完播率、3 秒退出等）超过 5 个点；个数类（24 小时播放）中位数低 20% 以上。
   - 区间完全落在「更差」一侧：「B 更差」。
   - 其他情况：「没有分出差异」，同时写明这次样本量能测出的最小差异。

**终点**：两个条件同时设，先到哪个就按哪个：每组样本数达到 `per_arm`，或者开始后过了 `max_days` 天。到终点后立刻停止分组，然后进入**收尾期**（默认 5 天），等最后几天建的稿件发布、满 48 小时、读到数据。收尾期结束后算出结论并存一份快照，之后不再改写；到那时还没有数据的算缺失。

**安全止损**：两组各满 15 条有数据后，如果 B 组 24 小时播放的中位数不到 A 组的一半，或者 B 组的缺失率比 A 组高 20 个点以上，tab 里提示「建议提前停止」，由用户决定。提前停止只能用来止损，不能用来提前宣布 B 更好。

**成本**：每组显示平均每条的模型花费和出片耗时，数据来自现有的用量统计。决定采用之前，把成本一起考虑进去。

**要跑多久**：按每组每天约 3.7 条估算（11-04 核对：自动视频每天约 7.4 条发到 B站，50% 分组），样本量取 80% 把握、α=10%（和上面的 90% 区间一致）。表是按均值估的，判定用的是中位数，中位数的效率略低，实际要的条数可能多一两成；分层又会让它少一些，两者大致抵消。

| 主要指标 | 要测出的差异 | 每组需要 | 大约天数 |
| --- | --- | --- | --- |
| 3 秒退出（波动 26.5） | 15 个点 | ~39 | ~11 天（有数据的只有 80%，约 2 周） |
| 3 秒退出 | 10 个点 | ~87 | ~24 天（约 4 周） |
| 封面点击（波动 36.3） | 15 个点 | ~73 | ~20 天（约 25 天） |
| 完播率（波动 17.7） | 8 个点 | ~61 | ~17 天 |

分层以后波动会小一些，实际需要的条数会比表里少。只在部分栏目上跑的实验，样本少，要跑得更久：比如只对整期节目生效的改动，7 天只有 8 条节目，每组每天约 0.6 条，凑够 50 条要 3 个月左右。所以 A/A 之后的第一个正式实验，要选对所有自动视频都生效的改动。

## 9. 「A/B 测试」tab

只有管理员能看到。

- **实验列表**：显示每个实验的名称、状态（草稿 / 进行中 / 已结束 / 已处理）、两组样本数、离终点还有多远、结论。
- **新建实验**：一步步填写：
  1. 选要改的开关（只能从登记表里选），填 B 的取值。
  2. 选范围：矩阵、栏目、单篇还是整期节目。
  3. 选主要指标和护栏指标。
  4. 设 B 组比例，默认 50%。
  5. 设终点（样本数、天数）。

  页面会按历史数据估算这个实验大约要跑多少天。
- **开始 / 暂停 / 结束**：开始前程序做校验，包括开关是否登记、取值能否通过栏目配置校验、和其他实验有没有冲突。暂停后不再分组，已有数据保留。
- **实验详情**：
  - 两组的样本数、待测数、实际生效率、SRM 检查结果。
  - 每个指标的两组中位数、差异、区间，没到终点的标「未到终点」。
  - 两组各自的视频列表，可以点开看。
  - 到终点后显示结论，以及「建议改动」。
- **每周复盘**：加一段「实验进展」，只读，列出进行中和本周结束的实验；复盘的视频列表里标出「实验 B 组」，免得实验期间把复盘里的变化误当成别的原因。
- **影响范围**：分组发生在建稿时，所以 B 组视频发到抖音、快手、小红书的版本也是 B。分析先只看 B站，tab 里写明这一点。

## 9a. 迭代循环

一次完整的迭代分七步：

```
① 想法 → ② 定义实验 → ③ 预览 B → ④ 运行 → ⑤ 结论 → ⑥ 采用 → 回到 ①
```

| 步 | 做法 | 解决的卡点 |
| --- | --- | --- |
| ① 想法 | 每周复盘的每条发现旁边有「为它建实验」按钮，点了生成预填好范围和指标的草稿；助手也能从对话中起草实验 | 想法散落在各处，要人工搬进 tab |
| ② 定义 | 草稿可以引用还没开发的开关，状态显示为「等待开发」；开关做好后自动变成「可以开始」 | 想法要等开发，开发不知道下一步做什么 |
| ③ 预览 B | 开始前，拿一条最近的视频，用 B 的设置重新出一版，**只出片不发布**，在 tab 里和 A 并排看，确认后才能开始。画面类、封面类开关必须预览；写稿类可以跳过，因为每次写出来本来就不一样 | B 上线前没人看过 |
| ④ 运行 | A、B 两组照常自动发布（见下面「运行中」）。首页自动化提醒会报告：实验开始、SRM 报警、建议止损、到达终点、结论出来。文稿详情、出片列表、复盘里都标出「实验 X · B 组」 | 实验跑几周，中途发生什么没人知道 |
| ⑤ 结论 | 每个结束的实验都存进「实验记录」，写明测了什么、结果如何、这次样本量能测出的最小差异。新建实验和以前的实验重复时，tab 会提示。助手也能读到实验记录 | 没分出来或 B 更差时，经验丢了，又测一遍 |
| ⑥ 采用 | 采用时，这个开关要对应现有配置里的一个字段；还没有字段的（比如只为实验新增的开关），决定采用时再加，没被采用就不用加。登记开关时不要求先有配置字段。点「去配置页」后，配置页预填好改动并高亮，用户确认保存，保存记录写明「来自实验 X」。采用范围默认等于实验范围；推广到没测过的栏目时会提示。配置页保留改动前的版本，可以一键回滚。不做采用后和过去比较的自动跟踪：那就是 §1 说不可靠的前后对比，会误报「优势消失」。想确认长期效果，就再建一个实验测一次 | 建议改动要人工去找字段，容易改错 |

### 运行中

A、B 两组视频都照常自动发布，不加人工确认。这是公平比较的前提：手动发布会让 A、B 的发布时段错开，还会变成挑着发，结论偏向 B。上线前由开始前预览（第 ③ 步）把关，上线后由安全止损（§8）兜底；发现问题时**暂停整个实验**，修好再继续，不能单独扔掉某一条。

这样现有的发布流程完全不用改：现有应用对 A/B 模块只有建稿处一处写入，加上 §2 白名单里的只读展示和一行启动。

**预览不破坏边界**：

- **预览出片**：现有的 `video_render.create` 会在出片表（renders）里建记录，不能直接用。A/B 模块另做一条预览路径：自己调 AutoVideo，出片和记录都写在自己的目录（`state/experiments/previews/`）和 `experiments.db` 里，不在现有的出片表里建记录，也不进入发布流程。开发时尽量复用出片的底层函数，只把记录写到自己那里。
- **预览不抢正式出片**：自动出片有并发上限（`video_autopilot` 的 `MAX_RENDERS`），预览走自己的路径会绕过它。所以同一时刻最多只出一个预览，并且只在正式出片没有在跑、也没有在排队时才开始（只读现有的出片状态判断）；否则预览排队等待，tab 里显示「等正式出片空闲」。

### 实验排队

改不同开关的实验可以同时跑（§7「冲突」），只有想测同一个开关的实验才需要排队：上一个实验结束（收尾期也结束）后，下一个自动开始。开始前照样做 §9 的校验和第 ③ 步的预览确认；预览还没确认的实验，排到了也不会自动开始，会提醒用户。

### 第一个实验先跑 A/A

A/B 模块上线后，第一个实验是 A/A：A、B 两组设置完全相同。正常结果应该是「没有分出差异」，而且没有 SRM 报警。这能验证分组、取数据、分析这一整套在真实环境里是对的。A/A 只检查流程，不需要足够的统计把握，所以终点设成每组 20 条（大约 6 天，加 5 天收尾期）。它不改任何开关，可以和第一个正式实验同时跑，不占排队。

### 测试 A/B 模块本身

- **边界测试**：§2 的四条。
- **分析引擎**：用造出来的数据测。已知 B 比 A 好 15 个点时，要判出「B 更好」；两组完全相同时，误判成「B 更好」的比例不超过 5%，误判成「有差异」的比例不超过 10%；样本不够时，要判「没有分出差异」。
- **端到端**：用假的写稿、出片、发布、取数据流程，走完从创建实验到结论、再到建议改动的一整圈。

## 10. 采用改动

到终点、结论是「B 更好」时，tab 里显示「建议改动」：要改哪个栏目或配方的配置、哪个开关、从什么值改成什么值。用户点「去配置页」，在现有的配置页面里看到改动、确认、保存，保存时走原有的校验。A/B 模块记下用户的选择：采用 B、保留 A，或者暂不处理。**A/B 模块自己不写任何正式配置。**

## 11. 存储

- 实验定义：草稿和正式的实验定义都只存在 `experiments.db` 里，不在 git 工作区产生文件。需要时在 tab 里下载。
- `state/experiments.db`（A/B 模块独占）：
  - `assignments(token, experiment_id, arm, column, block, assigned_at, code_version, script_id)`：`script_id` 由对账填上（§7「分组号」），对不上的丢掉
  - `settings(key, value)`：总开关等。读不到时当作关闭，`arm_for` 回答 A
  - 代码版本：进程启动时读一次 git 提交号并缓存，读不到记为「未知」，不在每次分组时调用 git
  - `applied(script_id, experiment_id, switch, applied, reason, at)`：B 组的改动是否真的生效
  - `events(experiment_id, kind, at, by, detail)`：记录开始、暂停、结束、SRM 报警、采用
  - `results(experiment_id, computed_at, data)`：结束时的快照，之后不改写
- 现有应用里只多出一项：参加实验的稿件的 `content_context.experiments = [{"id": "...", "arm": "B", "token": "..."}]`（A 组也写，用来对账），是建稿时写进去的，方便在稿件详情里看到这条视频属于哪个实验的哪一组。

实验定义示例（存库的内容，这里用 YAML 写出来方便阅读）：

```yaml
id: greeting_after_hook
name: 整期节目：问候放到要点之后
hypothesis: 整期节目开头先念问候和导读，3 秒退出 50%，单篇是 33%；先抛最抓人的一条，3 秒退出会下降。
# 注意：这个示例只对整期节目生效，样本太少（约 3 个月），只作格式示例，不作第一个正式实验（§8）。
status: draft            # draft → running → paused → ended → decided
scope:
  content_mode: episode  # 也可以写 matrices / columns；手动选题固定不参加
share_b: 50              # B 组占比（%）
arms:
  A: {name: 现状, overrides: {}}
  B: {name: 问候后置, overrides: {greeting_position: after}}
metric:
  primary: exit3s
  better: lower
  min_effect: 10
guardrails:
  - {metric: completion, better: higher}
  - {metric: views_24h, better: higher}
stop: {per_arm: 50, max_days: 28}
```
