# 控制台性能与稳定性巡检

日期：2026-10-25。范围：Research 控制台 16 个主要页面、6 个代表性详情入口，以及网关、Research 后端和 AutoVideo 服务的健康检查。

## 结论与生效状态

主要页面可以正常打开，没有复现持续的全站秒级阻塞；但矩阵页面出现过 2～3 秒的长尾等待，成片与发布、信息源、文稿页面的日常加载也相对偏慢。

已修复并测试三处源码问题：主事件循环同步写活跃状态、矩阵读取周期计划时重复打开数据库、网关冷启动期间重复拉起后端。初次巡检完成时只验证源码；后续已随助手工作台发布启用。

后续状态更新（同日助手工作台发布）：相关回归通过后，已更新托管网关并平滑重启 Research 后端，三项修复随之启用。原独立视频任务保持运行，启用记录见 `state/maintenance/assistant-workspace-20261025-final/activation.json`。下面的页面耗时仍是发布前样本，不能据此宣称发布后的整站耗时收益。

## 测量方法

- 已登录 Chrome，每个主要页面完整导航 3 次，等待标题和加载提示完成；浏览器缓存已预热。下表是包含浏览器自动化开销的可用等待时间，不是纯网络耗时或 Web Vitals，也不是冷缓存首访。
- 详情入口各测 1 次，用于寻找异常，不作为统计分位数。
- 34 个读取处理器在 SQLite 快照上各运行 7 次，随后补测两个平台概览。这些数字不包含 HTTP、鉴权、网关和前端渲染，不能直接称为页面加载时间。
- 对同类读取做 64 次、6 线程并发调用。没有触发研究、生成、上传或付费模型调用。

## 已修复的问题

### 1. 活跃状态写盘阻塞所有请求

`web/server.py` 的异步中间件原本直接同步写活跃状态。故障注入将这项写入延迟 3 秒后，响应和其他请求都受到阻塞；轻量 `/api/live` 也会被拖住。

改为响应发送后的后台线程执行，并保留原有响应后台任务；记账失败不影响业务响应。新增测试验证响应已发出时慢写仍在进行，同时 `/api/live` 能继续返回。它解释了一种跨页面卡顿机制，但不能据此认定所有历史慢请求都只有这一个原因。

### 2. 矩阵周期计划存在逐项重复读取

`web/routes/matrices.py` 原本逐计划构造调度存储、读取历史，改为单次存储、批量描述计划。相同基准的处理器中位数：

| 读取 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 矩阵列表 | 84.8 毫秒 | 25.2 毫秒 |
| 矩阵详情 | 133.6 毫秒 | 78.8 毫秒 |
| 矩阵日历 | 86.6 毫秒 | 20.0 毫秒 |

这些是隔离处理器收益，尚未通过现网部署后的浏览器复测确认。

### 3. 冷启动可能重复拉起后端

网关原本主要依赖端口占用和冷却时间判断启动状态。Uvicorn 启动预热期间可能尚未监听，冷却过期后的请求会再次启动后端。历史网关应用日志最近 10,000 行中发现 16 次地址占用失败，说明值得处理这一风险。

现在跟踪网关自己启动的子进程；它存活期间不重复拉起，退出后仍允许重试。新增测试覆盖预热超过冷却时间、连续请求以及子进程退出重试。没有为验证而中断线上后端。

## 稳定性验证

- 64 次隔离读取、6 线程：零失败，中位数 326 毫秒，P95 640 毫秒，最大 692 毫秒；不是线上 HTTP 压测。
- 本机 40 次健康探测、2 线程：全部 HTTP 200。后端存活中位数约 10 毫秒、网关存活约 21 毫秒、Research 依赖健康约 46 毫秒、AutoVideo 健康约 1 毫秒。
- 网关、矩阵、调度与读取性能相关测试：127 项通过；活跃状态、网关、静态资源恢复、健康锁与助手接口等组合回归：106 项通过。两组有重叠，不应相加称为独立测试总数。
- 前端请求恢复与看板、报告、周期调度相关测试：5 个文件、64 项通过。覆盖刷新失败保留数据、过期请求保护、调度保存失败等。
- 网关应用日志最近 10,000 行未发现 HTTP 5xx；这不是全历史无故障保证。历史应用日志仍有 1～6 秒慢请求，包括存活探测与平台概览。

设置页提示 `opencode zen（按量计费）` 的 `deepseek-v4-flash` 不在当前清单中。这属于需要核对的模型配置问题；本轮未修改模型、密钥或发起付费验证。周期调度显示的旧 LaunchAgent 删除提醒是已有状态，不能算成此次页面加载失败。

## 后续优先级

1. 与平台功能统一发布三项修复，再按相同方式复测矩阵详情和偶发长等待，补充请求级追踪，区分网关、鉴权、排队、处理和下载耗时。
2. 优先缩小文稿、成片与发布的列表响应，改为服务端分页；不要只在前端隐藏已全量下载的数据。
3. 将页面模块按路由延迟加载，减少首次访问解析开销。当前主业务包约 610 KB，另有 React、Markdown 独立包；约 3.7 MB 的 YAML 编辑器已经是延迟加载，不能算入每页必需下载量。
4. 单独定位信息源的前端等待：接口本身快，继续加后端缓存预计收益有限。

本轮未覆盖低性能设备、冷缓存/弱网、千条以上业务列表、长时间耐久测试、真实发布或模型生成，以及所有配方/账号编辑子页面。因此结论是当前主入口可用、已定位具体风险，并非所有场景都已验证稳定。
