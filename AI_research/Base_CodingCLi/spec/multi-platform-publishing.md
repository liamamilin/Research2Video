# 多平台发布管理设计

2026-10-25；一期已实现并在本地服务验证。B 站、抖音已经真实使用；扩展阶段新增快手、小红书、微信视频号，接入统一分发模型，真实账号和投稿验收待完成。

当前决定（2026-10-25）：微信视频号按用户要求隐藏并暂缓使用，保留代码与状态，后续有明确需求再恢复。当前入口只显示 B 站、抖音、快手、小红书；快手和小红书已完成真实账号连接及登录态复验。细节见 [平台扩展记录](platform-expansion.md#微信视频号暂缓决定2026-10-25)。

## 现状核对

问题来自发布状态的聚合和页面入口，不是成片只能上传一次：

- `publications` 已允许同一文稿有多条记录，且含 `platform`、`version`、`render_id`。两个平台的候选查询分别排除本平台已发布记录，本来就允许复用同一成片。
- 文稿详情的 `platform_uploads` 只查询 B 站任务，没有聚合抖音任务。
- `PublicationFlow` 的 `published` 查找只匹配版本、不匹配平台，却显示“发布到哔哩哔哩”；会把其他平台的记录当成本平台已发布。
- 文稿列表、成片列表及下一步提示把“任一平台已有记录”归成一个“已发布”；部分入口因此消失，默认“未发布”也会隐藏仍能分发到其他平台的成片。
- 手动补录界面写死 B 站，前端没有传平台；后台模型已有平台字段，但其他平台的链接校验、账号归属、作品 ID 规范化尚未统一。

## 用户看到的关系

```text
文稿 v1 → 成片 video.mp4
             ├─ B 站 / 账号甲 → 独立发布包、任务、作品、状态
             ├─ 抖音 / 账号乙 → 独立发布包、任务、作品、状态
             └─ 未来接入的平台 → 相同结构
```

制作状态和发布状态分开。文稿仍显示草稿/定稿，成片仍显示生成中/成片完成；发布区分别显示各平台状态。

摘要使用“已发布至 1 个平台”，不再用一个“已发布”覆盖所有平台。没有明确选择目标平台时，不显示“全部完成”或“还差几个平台”。未接入的平台不算待办。平台数按平台去重，同一平台有多个账号或多条作品不重复计算。

## 文稿发布页

在所选成片与版本下方，增加一个“发布到各平台”列表。推荐列表式布局，平台增多时便于对照；卡片式作为可比较的界面备选，业务规则一致。

每一行显示：平台、账号、该版本在该账号的状态、对应操作。

- 已发 B 站：查看作品、查看记录。
- 抖音未发布：准备发布。展开本平台的发布包，沿用所选成片及通用素材；编辑后明确确认提交。
- 上传中/排队中：查看该平台任务，不出现第二次提交按钮。
- 已提交：显示作品 ID 与“待公开确认”；仅在平台明确返回审核状态时显示“审核中”。
- 失败：显示原因，确认未提交的任务可重试。
- 结果不确定：核对作品，取得明确结果前不开放重投。
- 未连接账号：提供连接入口；不改变其他平台的状态。

B 站行的状态不会隐藏或禁用抖音行。给抖音编辑标题、简介、话题、封面时，保存的是抖音发布包，不修改 B 站已提交信息或通用素材。

发布编辑器由文稿页和平台管理复用：文稿页围绕一条成片展开，平台管理围绕一个平台管理全部任务。两处读取同一份状态和记录。跳转任务详情时携带平台、任务、文稿版本，返回后仍定位同版成片。

## 状态与操作

| 状态 | 证据 / 含义 | 操作 |
| --- | --- | --- |
| 未发布 | 此版本在此平台账号下没有投稿或发布记录 | 准备发布 |
| 待发布 | 已保存该平台发布包，尚未提交 | 编辑并提交 |
| 排队中 / 上传中 | 有且仅有一个有效投稿任务 | 查看进度；排队时可取消 |
| 已提交，待公开确认 | 平台接受并返回作品 ID，未确认公开 | 查看作品、核对结果 |
| 审核中 | 平台明确返回审核中 | 查看进度 |
| 已发布 | 平台确认公开，或用户明确手动补录已发布事实 | 查看作品；标注确认来源 |
| 发布失败 | 平台明确拒绝，或确认提交前失败 | 查看原因；满足安全条件后重试 |
| 结果待核对 | 提交后超时、中断，或缺少可靠回执 | 核对结果；不自动重投 |
| 已下架 / 私密 | 后续检查明确发现可见性变化 | 保留历史，显示当前可见性 |

“没有确认公开”不等于“审核中”，也不等于“发布失败”。网络查询失败只更新检查结果，不把已确认发布的作品降级为失败。首评/置顶失败独立显示，不把视频发布状态改成失败。

## 多条发布记录

下方保留发布历史，按平台分组；默认当前成片版本，可展开所有历史版本。

每条真实作品记录至少包含：

- 平台、账号（旧记录无法确认时标“账号待核对”）。
- 文稿版本、使用的成片、投稿时标题。
- 平台作品 ID、链接、提交时间、公开时间或手动填写的发布日期。
- 来源：平台自动确认 / 手动补录；最后核对时间、当前可见性。

投稿尝试和发布记录分别保存：失败尝试留在任务历史，不生成假的已发布记录。重试同一作品不重复生成发布记录；真实存在的不同作品可有多条历史，不能用后来一次覆盖原来的链接、日期。已有发布作品与另一条待核对任务并存时，同时显示已发布数量和该任务状态，不把已发布事实清空。

手动补录改为：平台 → 账号 → 视频链接 → 发布日期 → 确认记录。根据链接辅助识别平台，再让界面显示识别结果；平台与域名不匹配时拒绝保存。

手动补录表示用户确认已发布，标“手动记录 · 未自动核验”；不能冒充平台已验证。与后续自动回执指向相同平台作品时合并确认信息，保留来源历史，不重复计数。

移除本地关联不删除远端作品。已有投稿回执仍保留，不能通过删除一条本地记录自动恢复为可重复投稿。

## 列表与筛选

- 文稿列表/视频看板：制作阶段与平台发布标签分列，如“成片完成 | B 站已发布 · 抖音未发布”。
- 成片与发布：一条成片一行，展开各平台状态；无论任何其他平台是否发布，始终可查看分发入口。
- 平台管理：B 站只按 B 站状态筛选，抖音只按抖音状态筛选；“当前定稿”仍是成片范围，与发布状态筛选分开。
- 需要查“哪些视频还没发抖音”时，选择“平台：抖音 + 发布状态：未发布”。
- 全局“从未发布到任何平台”作为明确命名的独立筛选，不再和“当前平台未发布”混用。
- 升到 v2 后，v1 的发布记录保留；v1 已发布不把 v2 标成已发布，也不妨碍 v1 再发其他平台。

## 数据与服务约束

逻辑发布目标以 `文稿 + 版本 + 平台 + 账号` 确定。所选成片 `render_id` 和内容摘要作为该次投稿的固定来源，不因后续重出片、换稿、切账号而漂移。

- 一个逻辑目标可有发布包草稿、投稿尝试历史和多条真实作品记录。
- 默认同一目标只允许一个有效投稿；同版重新渲染不会绕过防重复限制。另发一条作品需要明确的新发布意图，首期不自动执行。
- 不同平台或不同账号的目标相互独立；某平台失败不回滚、覆盖或重试其他平台。
- 作品按“平台 + 平台作品 ID”识别，URL 只作展示；规范化后合并带追踪参数的同作品链接。账号是归属校验，不靠标题或当前登录账号猜测。
- 凭证不进入通用发布数据、文稿详情或前端。通用接口仅返回账号标识与昵称。

先增加统一的发布状态读取层，聚合现有 B 站 outbox、抖音队列和 `publications`；各上传 worker 继续独立运行。页面使用同一 `distributions[]` 结构，不再从第一条 publication 或单一 B 站任务推断状态。

建议新增按版本读取的分发概览，字段为平台、账号、标准化状态、当前任务、发布记录、可执行操作、最后检查结果。现有 `published` 可短期保留为兼容的“至少存在一条发布记录”派生字段，所有跨平台入口与候选筛选改用目标平台状态。

## 迁移与首期验收

保留已有视频、B 站记录、抖音作品 ID、任务和凭证。新增平台账号、作品标识与确认来源信息；旧记录不凭当前登录态强行补账号，无法确定的版本不套到新稿上。

一期同时改文稿发布页、成片与发布、文稿列表标签、手动补录和统一状态接口。平台能力先覆盖现有 B 站与抖音，后续平台按同样规则接入。

验收必须覆盖：

1. v1 已发 B 站后，仍能选原成片准备抖音发布；不会重新生成视频。
2. B 站已发布、抖音未发布/上传中/失败/待核对分别正确展示，互不影响。
3. 两个平台成功后，文稿保留两份作品记录、两套发布包和两个实际链接。
4. 查询“抖音未发布”能找到已发 B 站的成片；全局未发布筛选含义明确。
5. 切换账号、文稿版本或重出片不会错绑、覆盖旧作品或产生重复投稿。
6. 手动补录平台、域名及作品 ID 匹配，相同作品的手动与自动记录可合并。
7. 缺少作品 ID 的不确定结果不会被误标为已发布，删除本地记录也不会自动重投。


## 一期实现与验证（2026-10-25）

- 文稿发布页采用平台列表，复用平台管理中的 B 站、抖音编辑器；可分别保存发布包草稿。队列中的发布包保持原始快照，任务详情可展开查看。
- 文稿、成片与发布页面支持平台及目标发布状态筛选。制作状态保留定稿/成片完成，发布摘要按平台去重。
- 手动补录包含平台、账号、链接及日期；校验平台域名并规范化作品 ID。完整链接的同作品手动/自动回执合并确认来源，不覆盖不同作品。
- publications 增加账号、作品 ID、确认来源、确认时间及本地移除时间；distribution_drafts 按文稿、版本、平台、账号保存。原始视频、凭证和上传队列保留。
- 移除本地记录保留防重；再次明确补录同作品可恢复本地关联，自动轮询不擅自恢复已移除的记录。旧记录只在作品 ID 与已确认队列回执精确匹配时补账号；未知版本不归入当前稿。
- 完整检查通过：2219 项 Python 测试、3 项跳过；最终 UI 回归 457 项通过。发布专项另含账号切换、历史版本、草稿隔离、手动/自动去重、移除后防重、输入和权限校验。
- 实际界面验证：已发 B 站的 `601颗星…` 成片可展开抖音编辑器，也能在“抖音 + 未发布”查询中找到。已有抖音作品 7700436961890209034 仍为已提交、待公开确认；验收未创建新的真实投稿。
- 服务升级前用 SQLite backup 保存三份数据库；升级后原 38 条 B 站发布记录保留，其中 32 条按已确认回执补账号，6 条保持账号待核对。健康检查确认新后端实例运行。

当前限制：未知账号的旧记录需人工补录同一链接并选择账号来确认归属；短链接没有可离线确认的作品 ID 时保留原记录，不猜测与完整链接的对应关系。当前只连接每个平台的一个账号，历史账号状态独立保留；未接入的平台不显示为待发布目标。

## 扩展平台接入

快手、小红书和微信视频号复用 `distributions[]`、发布包草稿和手动记录，以平台、账号、文稿版本分别确定目标；各自队列和浏览器适配器隔离。新增平台未连接时显示“未连接”，不会将五个平台都算作必须完成的分发任务。

三个适配器目前均没有可靠的自动公开确认能力；快手仅提供准确作品 ID 的账号归属核对。取得投稿回执不写成已公开，没有 ID 的不确定结果不重投。手动补录仍标明手动来源，视频号 sph 分享码不作为平台作品 ID。首评、置顶和统计数据按独立能力关闭，后续真实验收再逐项启用。实现与验证见 [平台扩展](platform-expansion.md)。
