Claude Code 一天能派 500 个活，但额度会先见底

你手上三个 issue 要改，两条调用链要查，还有一份变更说明要写。以前这是三个 Claude Code 会话，每个贴一遍仓库路径和相关文件，最后自己把结果拼起来。Anthropic 现在让你只开一个——在一段对话里把活派出去，它自己拆成并行线程。
大家好，我是洛洛，今天我们聊聊 Claude Code 的 Projects。它九月就发了 beta，十一月十四号文档更新，把 Ultra 加进可用计划，写明每天最多新建 500 个线程。但我想说的不是这个数有多大，是它背后那笔账怎么算。
变化本身很具体。以前 Projects 像个文件夹，里面装几个对话；现在主界面是一段协调对话。你在里面打字——“修这三个 issue”“调研这两处调用链”“按 diff 写变更说明”——Claude 自己判断哪些话留在对话里回答，哪些变成一条线程派出去。每条线程是独立会话，有自己的上下文窗口；云线程在自己的分支上跑，需要时开合并请求。
你合上笔记本，它还在跑。手机上能看到哪条完成了、哪条卡住了、哪个合并请求可以合。项目还有共享记忆和一个资料库，线程产出的文件收在里面。这是它和“多开几个窗口”最大的区别：不是并行跑完就散，是一串活接着往下走。

代价藏在额度里。每个线程都是一次完整会话，协调对话本身也在消耗调用量。你开三条线程，就是三份会话在跑，再加一份协调，比单会话更快撞到套餐上限。
还有一种更隐蔽的消耗：盯合并请求的线程。CI 失败或者有人留评审评论，它会再次唤醒，再烧一次额度。你以为活干完了，它半夜又醒过来。撞上限的线程不会死，它会等，默认在限额重置后自动继续——所以第二天早上你打开手机，可能看到三条线程整整齐齐停在“等待额度”。

可用范围也比想象中窄。Projects 现在面向 Pro、Max、Ultra，逐步放量；Team 和 Enterprise 还不行。入口在 claude.ai/code、桌面端的 Code 标签页和 Claude 手机 App；终端 CLI、VS Code 扩展、JetBrains 插件里都没有，也不走 Bedrock、Google Cloud 的 Agent Platform 和 Microsoft Foundry。
我更看重的是它不继承什么。云线程拿到项目仓库和文件、指令和记忆、你 claude.ai 账户上的连接器，还有一个配好网络访问和环境变量的云环境。它会读仓库里的 CLAUDE.md，但不继承仓库自带的技能配置、不继承设置文件、也不继承 MCP 配置。这个边界不注意，你会以为它什么都能用，结果一跑就缺配置。
如果你那条线程需要本机才有的东西——本地数据库、设备模拟器、VPN 后面的 API——得让它通过远程控制在你的机器上跑。本机 Claude Code 要 v2.1.280 或更新，而且 claude.ai 设置里那个 Require trusted devices 开关必须关掉。已经开着的本地会话不能变成项目线程，只能把活带进来。
还有两件事别指望它替你解决：两个线程改同一处代码，照样合并冲突；beta 期间项目属于单个用户，没有组织级控制。

我的建议是：先别急着把所有活都搬进去。如果你的任务天然能拆成几条互不依赖的线——多仓库迁移、实现和测试并行、一边改代码一边写变更说明——现在值得试，但从两三条线程开始，盯着额度用。反过来，如果你的活是一条线走到底，或者你们团队要组织级权限、要审计，现在切过去收益有限。Projects 不会让你的串行任务变快，只会让你更快撞上限。
回到那个周五下午。三个 issue、两条调用链、一份变更说明，你现在可以在一段对话里派出去，合上笔记本，手机上收合并请求。但第二天早上你更可能遇到的，不是任务没跑完，是额度先见底。这才是这个 beta 现在真正的门槛——不是它能不能并行，是你付不付得起并行的账。
你手上现在的活，能拆成几条真正互不依赖的线？如果拆完发现只有一条，那 Projects 对你来说就是个更贵的单会话。我是洛洛，我们下期见。
