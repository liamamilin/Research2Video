## 优先处理的问题

### 搜索额度耗尽与降级重复探测

**P1，外部依赖故障及恢复策略缺口。** 截至 21:45 的当天运行日志中，Exa 额度耗尽相关 402 共 92 条，Exa MCP 限流 429 共 6 条。日志明确出现 `NO_MORE_CREDITS`，正在执行的研究和页面采集受到影响。

当前已经配置 `exa → exa_mcp → youcom → duckduckgo` 的备用链路。`core/search.py` 的每次 `search()` 都重新从首个提供商开始，并将本次 `errors` 清空，没有跨搜索调用保留额度耗尽或限流冷却状态。因此后续查询仍会重复碰到已知不可用的前置服务。现有本地健康检查仍可能返回 `ok`，不能据此判断搜索依赖可用。

处理顺序：先确认账号额度和已有备用服务的可用性；在代码中分别处理额度耗尽与短期限流，保留已有备用链路，记录恢复时间与降级原因。通过已有运行结果展示外部依赖状态，避免增加重复的远端探测。不要因这一问题重跑原任务或重新投稿。

### 快手核对暂停与页首提示冲突

**P1 运营阻断，P2 展示 Bug。** 正式平台页面显示连续 21 次账号核实失败，作品回查和评论核对已暂停；同页页首仍显示“账号已核验 · 自动核对已开启”。截图保存在本轮证据目录。

`ui/src/components/SocialPublishing.tsx` 第 167 行只依据 `account.connected` 和平台能力生成页首文字；下一行才单独依据 `account.session.state === "expired"` 展示暂停提示。这两个状态没有统一优先级。

应让页首同时反映会话健康与回查的实际运行状态，并通过原平台连接入口核实当前独立浏览器会话。本轮没有重新扫码或尝试投稿，不能只凭“已连接”标签判断登录仍有效。小红书当前还分别存在上传登录和评论登录状态，应继续区分两者。

### 默认测试命令收集历史验收代码

**P2，验收入口 Bug。** `scripts/check.sh` 第 22 行运行无目录限制的 `pytest -q`。本轮在工作区执行对应的仅收集检查，出现 **865 个收集错误**；报错指向 `state/validation` 中多份历史测试副本，错误为 `import file mismatch`。

明确限定正式 `tests` 目录后，后端完整回归通过。因此这些收集错误不等于 865 个产品功能故障。应为 pytest 设置正式测试目录并排除运行、验收输出目录；保留历史快照，无需删除数据库、历史制品或旧测试来绕过错误。脚本使用 `set -e`，当前收集失败还会阻止后续配置与前端检查执行。

### 队列积压和实际执行状态没有分开

**P2，容量与可观测性问题。** 21:32 的数据库快照有 81 个 `RUNNING` 自动批次、81 个 `PENDING` 和 16 个 `WORKING` 条目。检查其中批次的来源，76 个来自推荐主题，5 个来自报告生产；并不是 81 路模型同时运行。

当前执行器 `MAX_SCRIPTS=2`、`MAX_RENDERS=1`，采样时实际约两篇研究或写稿、一个渲染。大多数批次在等待执行槽；不能把它们未经执行器证据判断为卡死。排队规模会延长完成时间，搜索依赖异常又会拖慢研究步骤。

优先把排队、研究、写稿、等待渲染和实际渲染分别展示，给出最老等待时间、完成吞吐和阻塞原因，再评估矩阵之间的执行顺序与公平性。本轮保留全部原批次，没有取消、补跑或改变周期，也不建议为让状态归零而清空队列。

### 列表响应仍偏大

**P2，性能优化空间。** 本地处理器的含 JSON 编码中位耗时最高约 181 ms；完整文稿列表约 1.54 MB，compact 版本约 468 KB；完整成片列表约 955 KB，compact 版本约 509 KB。这些是未压缩 JSON 字节数，不等同于实际网络流量。

列表同时携带较多历史与制作信息，数据增长后会加重序列化、解析和页面更新。下一步适合继续做服务端分页、按视图选择字段、详情按需读取，并保留原版本与发布状态的正确归属。

浏览器内容就绪的单次有效观察约 0.4 至 5 秒。部分复测遇到浏览器自动化选择器约 3 秒的等待上限，已标为无效样本，不能当成应用接口超时，也不能据此发布可靠的 P95。当前负载包含正常研究、视频制作和其他会话操作，部分采样还与本轮隔离测试同时运行；后续性能修复应在同一路径、相近负载下比较。

### 研究中的文稿详情标题为空

**P3，界面 Bug。** 实际打开研究中的文稿时，选题段落有完整标题，但 H1 为空。`ui/src/pages/VideoScriptView.tsx` 第 393 行使用 `shown?.title ?? detail.title`，没有在无版本或空标题时回退到 `detail.topic.title`。

应补充选题标题和最终默认标题的回退，并覆盖研究中、写稿中、空字符串标题和已有版本四种状态。该文件仍有其他会话的未提交改动，本轮仅记录问题。

### 部分来源持续抓取失败

**P3，采集维护问题。** 既有调度日志中，一条 YouTube RSS 在连续两天返回 404；两个 OpenAI 案例目录入口出现“没有解析到内容条目”。这些与 Exa 额度不足应分别统计，避免把解析、地址不可用和账号额度问题合并成笼统的“抓取失败”。本轮没有为了验证而重新搜索或采集来源。

## 不应误判为新增系统故障的记录

21:32 的当天出片尝试采样为 28 次完成、1 次失败、1 次取消及 1 次进行中；按每个文稿版本的最后一次尝试统计，为 27 个完成、1 个取消及 1 个进行中。一次历史失败已有后续完成，不能把全部重试当作最终失败率。

截至补查时，32 篇“候选主事件均已占用或覆盖”的 `FAILED` 文稿全部已经归档。当天没有发现其他类型的新增文稿失败。自动批次会取消对应的无新选题条目，继续处理其他条目；这属于排重后的正常跳过，运营统计应与技术故障区分，保留原尝试记录。

调度页的两条旧系统任务已删除提醒仍然可见，本轮未恢复它们。生产中的排期和手动运行策略保持原样。浏览器日志中的几条监听器警告来自扩展脚本，没有将其算作研映前端异常。

## 建议修复顺序

1. 搜索额度与限流的降级、冷却和依赖状态展示，先降低正在发生的失败与重复等待。
2. 快手会话核实及平台状态统一，保留原投稿和回查记录。
3. 修正默认测试收集范围，让仓库约定的验收命令可靠完成全部检查。
4. 将队列等待与真实执行分开，随后处理列表分页与字段体积。
5. 补齐研究中文稿标题回退及失效来源诊断。
