# B 站投稿异常恢复

## 问题与范围

两次投稿在原生 `biliup upload` 阶段以退出码 1 结束，原日志只保存了“连接失败或超时”。原流程将这类结果记为 UNKNOWN 后不再查稿，任务一直停留在人工核对状态。

本轮保留现有账号、原任务、发布包、成片与发布记录，补齐提交前传输重试、结果不明时的自动查稿和可读的恢复进度。个人品牌资产及原创旋律未参与修改。

## 实现

- 针对已安装的 biliup 1.3.4，核对官方源码中的顺序：登录、封面、文件传输、最终稿件提交。诊断只解释终止错误，不把日志里较早的失败当作本次退出原因。
- 区分预上传、封面、上传初始化、分片传输、合并及最终提交。只保存阶段、允许的请求域名、错误类型、HTTP 状态、耗时和次数；不保存原始 CLI 输出或含凭证的请求 URL。
- 明确发生在最终提交前的临时传输错误，最多尝试三次，间隔退避。最终提交连接中断、进程中断、未知请求和仅有笼统错误时继续保留 UNKNOWN。成功的 BV 回执不会因进程之后异常退出而丢失。
- UNKNOWN 自动通过账号绑定的创作中心接口查稿，包含进行中、已通过和未通过稿件。按标题搜索，再校对完整标题、简介、分区及提交时间窗口，唯一匹配后以事务绑定 BV 号，继续等待公开或恢复发布记录。
- 空检索不构成可重投证据；歧义和已被其他任务使用的 BV 号不会自动关联。原有 BV 号优先直接核对。查稿次数、退避时间与进度持久保存，重启后继续，每轮后台只处理一个到期任务。
- 页面显示核对进度，提供“立即核对投稿结果”。该入口只核对原任务，不创建上传；角色、账号和 CSRF 检查沿用既有规则。

## 验证

- 提交前以 `1a5db9d` 为基线，仅叠加本轮 10 个暂存文件导出独立副本。投稿恢复、原 B 站适配器、首评、发布文案及平台数据相关回归 152 项通过，覆盖空检索实际返回 null、Rust 错误格式及并发回执占用等边界。
- 页面与分区组件 29 项通过；TypeScript、生产构建、相关 ESLint、Python 编译及 `git diff --check` 通过。
- 研究端渲染跟踪的恢复、并发与重启相关 6 项回归通过。
- 真实只读查稿使用同一账号，以一条已公开视频为对照，能够找到原 BV 号；两条异常任务按完整标题检索均为 0 条。
- 处理旧任务前备份平台账本，保存核对结果；原有其他 67 条投稿记录与 190 条发布记录保持一致，没有触发视频重投。

## 旧任务处理边界

两条旧任务已保存第一次核对结果并接入后台继续核对。旧诊断没有具体请求阶段，未把它们直接改成可重投状态，也没有重新生成视频。标题未检索到不能单独证明最终投稿从未被平台受理。

真实回放、账本备份、启用与后续自动核对证据仅放在忽略目录 `state/validation/bilibili-recovery-20261028/`，不纳入开源提交。研究端重载保持独立视频引擎运行，已有排队渲染继续使用同一引擎任务 ID。

修复已在本机启用，健康检查正常，新查稿 API 已加载。启用后后台自动完成两条旧任务各自的第二次核对，仍未找到匹配稿件，次数及下一次退避时间已持久保存；没有触发上传。再次核对原有其他 67 条投稿和 190 条发布记录保持一致。
