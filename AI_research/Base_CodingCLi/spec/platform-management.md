# 平台管理：哔哩哔哩上传与评论

调研与首版实现：2026-10-24。入口为研究控制台 `/platforms`，侧栏位于“成片与发布”之后。

## 三个项目的结论

| 项目 | 实际验证 | 采用方式 |
| --- | --- | --- |
| [77rickliu/bilibili-mcp](https://github.com/77rickliu/bilibili-mcp) | 隔离环境中用 bilibili-api-python 17.4.2、mcp 1.30.0 成功导入，发现全部 29 个工具。包含登录、评论读取/回复和视频上传。 | 用作协议与功能验证参照；首版后端直接调用同类 Web 接口，不运行上游运营脚本，也不依赖 MCP 进程管理。 |
| [biliup/biliup](https://github.com/biliup/biliup) | 安装官方 v1.3.4 macOS ARM64 二进制，核验发布 SHA-256，实测 `--version`、`upload --help`。支持 Web 投稿、封面、标签、分区和多种登录。 | 复用原生 CLI 执行大文件上传与投稿；不嵌入录播/WebUI 服务。 |
| [Janson20/BiliCommentBot](https://github.com/Janson20/BiliCommentBot) | 阅读评论分页、楼中楼、回复历史、限流与去重实现；它是独立 Flask/SocketIO 机器人，含自动回复和点赞策略。 | 参考收件箱、历史去重、root/parent 关系与频率控制。复用现有 FastAPI、React、SQLite，不并入第二套后台。 |

源码依据：[MCP 服务](https://github.com/77rickliu/bilibili-mcp/blob/main/mcp_server.py)、[biliup 命令](https://github.com/biliup/biliup/blob/v1.3.4/crates/biliup-cli/src/cli.rs)、[投稿实现](https://github.com/biliup/biliup/blob/v1.3.4/crates/biliup-cli/src/uploader.rs)、[评论机器人](https://github.com/Janson20/BiliCommentBot/blob/main/bot.py)。

需要区分的细节：

- MCP 的默认评论读取按热度排序，楼中楼只是预览，不能直接充当完整新增评论收件箱。
- 本地收件箱按时间分页。每次同步读取一页主评论及子评论预览；“继续读取更早评论”和“读取完整楼中楼”提供后续分页。
- biliup 投稿成功的进程日志目前不是稳定的 JSON 输出协议。适配器只接受成功响应中的 BV 号；上传命令开始后的失败进入结果待核对，不根据退出码猜测成功，也不自动重投。只读前检失败则明确标为投稿前失败。
- biliup 仓库 LICENSE 标示 MIT，但 README 同时含禁止商业用途的文字。打包分发或商业化之前，需要确认该表述冲突；当前安装为本机工具使用。

## 已实现的用户流程

1. 管理员在“账号与策略”使用与 biliup 一致的 BiliTV 扫码授权，或导入 biliup 的完整凭证 JSON。保留原生 access/refresh token 和平台字段，校验 token 与 Cookie 的 UID 一致；仅有 bilibili-mcp 网页 Cookie 时可管理评论，页面提示重新扫码补齐上传授权。服务器通过已登录的 `nav` 结果验证 UID；凭证不返回前端。
2. 在“视频投稿”查看全部文件可用、尚未发布或排队的成片，包含归档文稿、历史版本，以及文稿继续修改前已经生成的成片。支持搜索和范围筛选；同一稿同一版保留最近一次文件可用的渲染，不截断到前 100 项。读取所选成片对应版本的发布包，编辑标题、简介、标签和分区；归档、历史版本会明确提示。
3. 加入队列后，后台单并发执行 biliup。现有封面可用时自动附带，否则用 ffmpeg 截取第 3 秒（短视频回退至第 0 秒），投稿类型为自制。封面和上传检查点保留在任务目录。
4. 收到 BV 号后先显示“已投稿 · 待平台审核”。查询确认当前账号的视频已公开后，回写文稿发布记录并加入评论管理。
5. 在“评论收件箱”选择视频并同步；也可添加当前账号已有的 BV 号。支持草稿、发送回复、标记已处理/恢复、分页和原评论跳转。

首版不自动生成 AI 评论，不含删评、任意评论置顶、黑名单、账号矩阵、多 P、定时发布或审核驳回详情。投稿时可明确选择发送并置顶用户填写的首条评论，见下节。任务失败和未知结果可见；平台创作中心仍是审核结果的核对入口。

## 投稿首条评论

投稿表单新增可选的「视频公开后添加首条评论」、1–1000 字内容和「置顶这条评论」。管理员可直接「保存为常用评论」，或在「账号与策略」配置默认内容与置顶选项，供后续手动及自动投稿复用。每次手动投稿仍可修改、关闭。保存模板本身不会发送评论，也不会向已有投稿补发；新建投稿时将选项与内容快照写入任务，后续修改模板不影响已排队的任务。换号或断开时清空默认评论，避免串号使用。

视频必须经过账号归属及公开状态确认后才发送顶层评论；发送前再次确认公开状态。参考 [bilibili-api 的评论发送和置顶实现](https://github.com/inorilzy/bilibili-api/blob/main/bilibili_api/comment.py)，调用 `/x/v2/reply/add` 时不带 `root/parent`，取得确认的评论 ID 后先落库，再调用 `/x/v2/reply/top`。视频公开与评论、置顶状态独立，评论失败不撤销文稿发布记录。这是作者预设的首条评论，不保证早于所有观众评论。

- 评论：`DISABLED`（默认及存量任务）或 `WAITING → SENDING → SENT`。仅明确的 API 拒绝进入 `FAILED`，可由编辑者点击重试；网络中断、进程中断或未取得评论 ID 进入 `UNKNOWN`，仅提供跳转核对，不自动重发。
- 置顶：`DISABLED` 或 `WAITING → PINNING → PINNED`。失败或结果不确定时保留已发送评论 ID，按钮仅重试置顶，不重新发表评论，也不主动取消其他置顶评论。
- 后台与回复共用账号范围的发送节流，两次发送至少间隔 15 秒。后台使用既有跨进程 worker 锁，数据库原子认领任务，重启不会重发结果不明的评论。
- 投稿卡片显示评论原文、发送状态、置顶状态和原评论链接；失败时显示单独错误，不会把视频显示为投稿失败。普通查看者只读。

接口：投稿与策略请求增加 `first_comment: {enabled, text, pin}`；管理员可 `PUT /first-comment-template` 单独保存模板；编辑者可 `POST /uploads/{task_id}/first-comment/retry` 或 `/first-comment/pin/retry`。均沿用身份及 CSRF 校验，日志不包含评论正文或凭证。旧客户端保存其他策略时保留模板。

新增离线回归覆盖公开前等待、可选置顶、重复轮询与并发防重、发送/置顶分别失败、断点恢复、模板快照与换号隔离、共享节流、鉴权和数据库迁移；不使用真实评论做测试。视频数据 tab 属于后续设计，本次不增加。

## 文稿与平台的发布入口

文稿负责发布素材、版本选择和发布结果；平台管理集中执行投稿、审核状态核对和评论管理。两处使用 `video.db.publications` 中同一份发布记录。

| 所选文稿版本的状态 | 文稿发布卡片 | 平台管理 |
| --- | --- | --- |
| 已有成片、尚未投稿 | “投稿到哔哩哔哩”，携带具体成片和版本跳转 | 自动选中成片，编辑并确认后加入队列 |
| 排队、上传、待审核 | 显示实际状态和“查看投稿进度” | 聚焦该任务，保留返回同版文稿的入口 |
| 失败、取消、结果待核对 | 继续查看原任务 | 检查、重试或核对；不会另建同版投稿 |
| 已公开 | “已发布”“查看已发布视频”“查看平台记录” | 自动回填文稿版本、成片、链接和发布日期 |

收到投稿成功回执只进入待审核。仅在视频归属已确认、公开状态明确为 0 时回填；发布日期优先使用平台 `pubdate`，缺失时使用确认当天。文稿详情和列表的已发布标签由该版本的发布记录推导，不改动写稿/定稿状态；旧版发布不会把当前新版草稿标成已发布。

手动补录继续保留，并明确标为补录。相同文稿、版本和视频链接重复写入时复用记录；带追踪参数的 B 站同视频链接也会去重。成片版本与补录指定版本不符时拒绝记录。已手动补录的版本不会再发起新投稿，排队后补录也会在上传前停止重复投稿。

文稿详情携带当前连接账号的 `platform_uploads`，活动任务期间每五秒刷新，页面重新可见时也刷新；平台可通过任务 ID 直接读取旧任务，后台待处理查询不受总览最近 200 条的限制。

## 自动化范围

默认关闭。管理员连接账号、准备 biliup 并选择默认分区后，可以保存启用“出片后自动投稿”。

投稿页和默认分区均按名称选择完整分类路径，内部转换为 `tid` 传给 biliup。列表来自当前登录账号的创作中心 `/x/vupre/web/archive/pre`，只提供可见末级分区；按账号缓存六小时，连接失败时可使用上次列表并显示提示。尚未选择或原分区已不可用时，人工投稿需要重新选择。分区加载失败可重试，保留已编辑的标题、简介和标签。

分区选择器可输入搜索词，匹配名称、上级分区、官方说明和常见主题别名（如 AI、LLM），多个词共同筛选。支持方向键、回车、Escape、中文输入法、清除和结果计数。搜索不改变已有选择，点击候选或回车才选中，取消搜索会恢复已选分区显示。

投稿表单按当前编辑的标题、标签和简介提供最多三个分区建议，并显示内容依据。推荐在浏览器本地匹配，只选当前账号可用的官方分区，不硬编码分区编号、不额外调用模型。标题权重最高；排除简介的参考来源章节和链接，也忽略自动生成的通用 AI/快讯/开发者标签，避免科普、历史等视频被统一推荐到计算机技术。内容不足时不强行推荐。用户点击「采用推荐」后生效；修改内容会更新建议并保留已选分区。默认分区设置只提供搜索选择，不根据某一条视频改动全局策略。

- 只处理启用时间之后完成的成片，不补发存量视频。
- 使用当前定稿和发布包；账号 + 文稿版本唯一，避免同版多次渲染产生重复投稿。
- 自动投稿仍只处理未归档、状态为已定稿、成片版本等于当前定稿版本的文稿。手动列表扩大不会扩大自动投稿范围，自动任务出队时还会重新检查。
- 沿用流水线的事实质量阻断条件：严重问题、待核实、未审计。发布前时效复核提醒也会暂停自动入队，成片保留供人工处理。
- 另可启用每五分钟同步已管理视频的最新评论；自动同步不触发回复。
- 更换/断开账号暂停自动策略，已有任务、评论、草稿按 UID 隔离并保留。

手动候选列表显示总出片次数、文件可用版本数、已发布、已有任务和文件暂不可用的数量，便于核对缺失原因。发布包使用所选历史版的内容与章节，不会把当前新稿的标题简介套到旧成片。旧后端尚未重启时，页面会提示其仍返回旧候选列表。

## 状态与持久化

投稿：`QUEUED → UPLOADING → SUBMITTED → PUBLISHED`。

投稿前检查失败为 `FAILED`，取消排队为 `CANCELLED`，这两种可重新检查排队。进程中断、超时或回执不确定为 `UNKNOWN`，需要先到创作中心核对，再填 BV 号。`UNKNOWN` 不提供自动重投。

上传前先运行原生 CLI 的只读 `list --from-page 1 --max-pages 1`，走与上传相同的登录/令牌刷新逻辑，失败时不执行 upload。缺少令牌、未知平台、授权验证/刷新错误码显示为具体的投稿前错误；刷新后的凭证在账号锁内保存。进入 upload 后的网络错误仍视为结果不确定。任务目录中的 `diagnostic.json` 只保留阶段、退出码、允许列表内的原因和是否确认未投稿；后续尝试将此前结果保存在 `diagnostic-<timestamp>.json`，不保存原始 stdout/stderr、Cookie 或令牌。CLI 工作目录、可执行文件、凭证、封面和视频均使用绝对路径，避免切换 cwd 后文件不可达。

2026-10-24 首次真实投稿排查：网页扫码产生的 Cookie 被组装成 `platform=web` 和空 token，biliup v1.3.4 原生验证立即返回「未知平台」；仅去掉平台字段后仍返回 `credential validation failed with Bilibili code -400`。根因是网页 Cookie 与原生上传授权不等价，不能伪造空令牌补齐格式。[原生授权源码](https://github.com/biliup/biliup/blob/v1.3.4/crates/biliup/src/uploader/credential.rs)。

评论：`NEW / HANDLED → SENDING → REPLIED`；回执不确定为 `UNKNOWN`。同一条评论不能重复发送；同一账号两次回复至少间隔十五秒。重复同步不会覆盖已保存的处理状态或草稿。

数据位置（均为忽略的运行数据）：

- `<state_dir>/platforms.db`：策略、投稿队列、视频和评论记录。
- `<state_dir>/platforms/bilibili/credentials.json`：0600；只保留已知 Cookie 和原生上传授权字段。
- `<state_dir>/platforms/bilibili/account.json`：脱敏账号信息。
- `<state_dir>/platforms/bilibili/categories-<uid>.json`：0600；只缓存分区名称、路径、编号和获取时间，不保存创作中心返回的其他账号资料。
- `<state_dir>/platforms/bilibili/worker.lock`：跨进程串行锁；锁持有期间不能切换账号。
- 项目 `state/platforms/runtime/bin/biliup`：本机安装的投稿可执行文件。
- `<state_dir>/platforms/bilibili/uploads/<task_id>/`：0700；保留截取的封面与上传检查点，临时凭证用完删除。

凭证输入限管理员，投稿/评论操作限编辑者以上；所有写接口使用现有 CSRF 防护。普通查看者可读状态。CLI 不使用 shell，凭证经临时 0600 文件传递，不进入命令参数或日志。真实发送前会检查视频归属。

## 安装与运行

```sh
../.AI_research/bin/python -m pip install -r requirements.txt
../.AI_research/bin/python scripts/install_bilibili.py
```

安装器固定 v1.3.4 官方发布包及 SHA-256，覆盖 macOS ARM64/x86_64、Linux ARM64/x86_64，仅取出可执行文件，不解包其他路径。Python HTTPS 不可用时，可从 [官方发布页](https://github.com/biliup/biliup/releases/tag/v1.3.4) 下载对应包后执行：

```sh
../.AI_research/bin/python scripts/install_bilibili.py --archive /path/to/biliupR-v1.3.4-aarch64-macos.tar.xz
```

也可自行安装 CLI，并用 `AREC_BILIUP_BIN` 指定可执行文件。ffmpeg 优先使用 `AREC_FFMPEG_BIN` / PATH，本工作区也可复用 AutoVideo 的 macOS ARM64 ffmpeg。重启后端后进入 `/platforms`。后台每十五秒检查投稿队列；测试用 `AREC_NO_AUTOPILOT_LOOP=1` 禁用自动循环。

## 验证边界

已实测：MCP 导入及工具发现、biliup 命令参数、公开扫码接口生成二维码/未扫码轮询。离线回归使用隔离数据库、假上传器和假评论接口，覆盖投稿去重、换号隔离、中断、公开后回写、楼中楼和回复防重。

已用真实账号复现首条任务的授权失败，并核查该账号全部 346 条稿件没有目标视频；保留原任务快照后将其改为可重试的投稿前失败。用户完成 BiliTV 扫码后，已用修复后的上传器复用原任务成功投稿 `BV1QUHA6XEH8`，平台由审核中转为公开（`state=0`）；后台将文稿 v3、原成片 ID、链接和日期正确回填，任务为 `PUBLISHED`。未发送真实评论。

首次恢复投稿时，独立执行器与常驻后台使用同一个账号文件和 worker.lock，避免打断现有成片任务。随后完成五条失败出片的修复重跑，确认出片、写稿、复核、研究轮次均空闲后，已优雅重启研究控制台后端；健康检查通过，任务直读接口显示原稿件仍为已公开，完整投稿修复已加载。[成功页面](acceptance/platform-management/upload-repair-published.png)。
