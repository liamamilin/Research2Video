# 内容矩阵：领域 × 受众 × 内容类型 × 形态

状态：方案，2026-10-19，等用户对「待拍板」三项表态后开工。目标：把现在手写的三个栏目，变成由四个维度组合出来的「格子」，加受众、加类型、加形态时只写定义，不改代码；已验证的三格行为一个字不变。

「矩阵」在本仓库有两个意思，先分开：`spec/01-practical_information_matrix.md` 是**研究雷达**的分区（模型与定价、AI 编程工具……），决定去哪里找信息；本文是**视频格子**，决定拿信息做成什么视频。雷达分区是选题来源，不是本文的领域维度（见「待拍板」第 2 项）。

## 现状（读代码得到的事实）

- 一个栏目（`flash`、`point_short`、`deep_dive`）把内容类型和形态绑在一起：时长、段落字数、写稿器、画面形式、包装都写在同一份 YAML 里（`config/video_columns.yaml`，`core/video/columns.py`）。
- 受众不是维度：快讯里写死 `AUDIENCE = "开发者"`（`core/video/flash.py`），三个栏目的研究提示词和写稿规范里都有「对开发者意味着什么」这类措辞，选题里的「目标受众」只是一个字符串。
- 深浅（入门、进阶、专家）和语气（`config/video_styles.yaml`）已经是旋钮，深浅里有一句受众描述，但和受众没有挂钩。
- `video_render.create` 把 `creative_intent.purpose` 写死成「知识讲解」。
- 界面只用第一个栏目：`ui/src/pages/VideoScripts.tsx` 里 `const column = columns[0]`。
- 栏目键 `column_key` 存在文稿表里，研究任务名用它拼路径（`video/{key}_{id}`），所以键必须是不含 `/` 的短名。
- 栏目配置是**实时解析**的：快讯时长从 1.5 改成 1.25 分钟，旧稿的预算就从 391 变成 326。矩阵化后一份受众定义会同时影响很多格子的旧稿，所以要记版本。

## 设计

### 一、四份定义，组合成一个运行配置

| 维度 | 拥有的字段 |
|---|---|
| 领域 | 研究范围、一手来源偏好、术语表（含中文说法，以后给配音读音用） |
| 受众 | 默认深浅（引用 `video_styles.yaml`，不再另写一套）、可用语气、关心什么、证据侧重、动作是什么、钩子取向、选题评分口径、`creative_intent` 的受众 |
| 内容类型 | 研究提示词骨架、写稿规范、必需角色、选题来源、选题必填字段、包装里的栏目名和角标、**视频形式**（`allowed_forms`、`default_form`） |
| 形态 | 时长、声音、来源卡、包装时长、字号、**对视频形式的限制**（`forms`，不写表示不限） |
| 类型 × 形态覆盖 | 节数、段落字数、写稿器（legacy 或 adapt） |

**维度不是完全正交的**：节数、段落字数、写稿器同时取决于类型和形态。所以类型定义里按形态写覆盖，没有覆盖的形态就是这个类型不支持它，「一个知识点 × 长」这类无意义组合自然选不出来：

```yaml
types:
  quick_take:                    # 快讯
    name: 快讯
    source: flash_discovery      # 选题来自发现报告
    required_fields: [标题, 一句话, 变化]
    required_roles: [钩子, 行动]
    formats:
      short: {sections: [2, 4], paragraph_units: [20, 90], writer: legacy}
audiences:
  developer:
    name: 开发者
    depth: intermediate
    tones: [news, concise, explainer]
    cares_about: 对工作流、成本、API 和配置的影响
    action: 改代码或配置
    version: 1
formats:
  short: {target_minutes: 1.25, video_form: information_motion, voice_id: voxcpm_anchor, source_card: true}
```

合并时的优先级：受众限制语气，类型给默认语气，最后取交集；字段冲突时按「类型 × 形态覆盖 > 形态 > 类型 > 受众 > 领域」。冲突写进解析结果的 `notes`，不静默覆盖。

### 一（补）、视频形式不是第五个维度

**视频形式**（`video_form`）是画面怎么组织：用哪套版式和组件。AutoVideo 现在认 `information_motion`（信息动效）、`process_diagram`（流程图解）、`auto`（模型在前两种里选），还有历史遗留的 `knowledge_cards`（AREC 不用）。

- 它主要由**内容类型**决定：教程适合流程图解，快讯、对比、盘点适合信息动效。所以放在类型下，不单独成维度（否则格子数再翻几倍，多数组合没有意义）。
- 类型写 `allowed_forms`（能用哪些）和 `default_form`（默认哪个）；每个形式在定义里带一句「适合什么内容」，界面上提示。
- 形态只有**限制权**：写 `forms: [...]` 就只允许其中的形式（例如以后竖屏只支持部分形式）；类型和形态允许的形式取交集，没有交集的格子不能选。
- **创建文稿时可选形式**，默认用类型的 `default_form`。选的形式记在文稿上，出片时用它。同一个「一个知识点」既可以用信息动效，也可以在内容适合时用流程图解，不用多一个格子。
- 与**风格**分开：形式是画面结构，风格是长什么样（配色、字号、角标、片头片尾）。风格已经在栏目的包装套件里，属于品牌那一层，不需要新维度。
- 其他形式（数据故事、代码演示、金句字卡、真人出镜加配图等）AutoVideo 目前都没有，每种要先做组件和版式，再回来登记。矩阵里先留好位置，不提前加。
- 现状：三个栏目的 `video_form` 现在写在形态里（快讯和知识点是 `information_motion`，深度解读是 `auto`）。第 2 期把它移到类型下，三格的解析结果不变（黄金快照守住）；`allowed_forms` 首期按现有写：快讯、知识点只有 `information_motion`，深度解读 `auto`、`information_motion`、`process_diagram`。

### 二、`Column` 变成解析产物，消费方不动

`video_columns.get(config_dir, key)` 的签名不变，`key` 变成格子 ID，内部做组合，返回现有的 `Column`。`video_workflow`、`video_render`、路由里的六七处调用一处都不用改。

- **格子 ID 是 slug**，由四个维度的短名拼成，例如 `ai-developer-quick_take-short`，不含 `/`。
- **旧键做别名**：`flash`、`point_short`、`deep_dive` 指向对应格子，旧文稿的改写风格、出片都不能坏。
- **版本**：每份维度定义带 `version`（沿用 `video_styles.yaml` 的约定，改一次加 1）；文稿版本里记格子 ID 和各维度版本。仍然实时解析，不做完整快照，但出问题能查到当时用的是哪一版。

### 三、受众成为真维度

- 受众定义引用默认深浅，再补深浅管不到的部分。开发者的动作是改代码或配置；决策者的动作是做决定或定预算；非技术人员的动作是去哪里打开哪个设置。
- 提示词里「开发者」这类词变成插槽（受众名、关心什么、动作），去掉 `AUDIENCE` 常量。
- `creative_intent` 的 `purpose`、`audience`、`tone` 改由格子填，画面规划按受众调整，AutoVideo 一行不改。
- **持续成本**：受众改变的是选题，决策者的快讯和开发者的快讯不是同一批新闻。每加一个受众，发现任务可能要新增一个（或给现有任务加受众口径）。这是持续成本，不是一次性开发。
- 非技术受众会放大英文术语的问题：术语是否需要解释、配音怎么读，都由领域术语表（含中文说法）提供。

### 四、新类型

| 类型 | 选题必填 | 选题来源 | 写稿 | 画面 |
|---|---|---|---|---|
| 盘点 | 主题、条目数 N | 发现报告，走类似 `from_report` 的路线：跳过研究，取前 N 条 | legacy，每条一节 | 现有组件，首期不改 AutoVideo |
| 对比 | 两个对象、对比维度 | 手写选题，或从深度解读的研究里切 | legacy | 已有的 `comparison`、`bar_chart` |

教程、观点放第二批。是否需要新角色（现在的 `ROLES` 是钩子、背景、概念、机制、证据、反方、行动、收束），在第 3 期读完盘点和对比的结构后定，需要才加。

### 五、启用清单，不是「所有合法组合都能选」

格子清单里每格一个状态：

- `enabled`：已有真实成片并通过检查。首期只有现有三格。
- `experimental`：定义了，没出过片。界面上标出来，不能被当成已验证。
- `blocked`：附原因，例如竖屏需要新的画面版本。

用户说先不跑真实测试，所以这期新加的格子全部是 `experimental`。

### 六、给第二个方向留接口，不现在实现

每个格子的流水线步骤（要不要研究、用哪个写稿器、跑哪些审计）写成声明式数据，首期只放现有步骤。短稿缺事实审计的缺口在「打磨链路」里接上。

## 开发顺序和完成标准

测试和黄金快照是离线的、几乎零成本，不属于「先不测试」：它们是保证三个已验证格子不被重构悄悄改变的唯一手段。

| 期 | 内容 | 完成标准 |
|---|---|---|
| 0 | 在当前代码上建**黄金快照**：三个栏目解析后的 `Column` 全字段、用固定选题填好的研究提示词、写稿规范、写稿器发给模型的系统提示 | 快照文件已提交 |
| 1 | 定义文件、解析器、别名、版本记录、启用清单、类型 × 形态覆盖 | 三格的解析结果和提示词与快照逐字节一致；旧文稿能改写风格、能出片（离线假 AutoVideo）；行为零变化 |
| 2 | 受众成为真维度：写「会用 AI 的非技术人员」一个新受众，提示词插槽化，去掉 `AUDIENCE`，`creative_intent` 由格子填；**`video_form` 从形态移到类型**（`allowed_forms`、`default_form`，形态的 `forms` 限制，创建文稿时可选并记在文稿上） | 开发者三格的快照仍一致，有意的差异写进提交说明；新受众的格子能用假模型离线生成文稿；选不允许的形式被拒绝；出片请求用文稿上记的形式 |
| 3 | 盘点、对比的类型定义、选题字段、选题来源 | 离线测试覆盖建稿和选题解析；格子状态 `experimental` |
| 4 | `GET /api/video/cells`（可选格子和不可选的原因）和界面格子选择 | 路由测试；只跑改动组件的 vitest（`SystemConfig.tsx` 的类型检查失败不是本工作引起的，汇报时写明） |

之后进入方向 2「打磨链路」：发布包（标题、简介、封面）、事实审计、初稿质量度量、选题到发布的衔接。
