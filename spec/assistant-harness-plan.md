# 助手 Harness：全应用控制开发计划

日期：2026-10-16

状态：已于 2026-10-16 获得连续实施授权，按下列范围开发。
实现与使用方式见 [助手说明](assistant-harness.md)，当前验证记录见 [开发进度](assistant-harness-progress.md)。下文保留规划时的基线事实。

## 1. 目标与使用方式

让用户通过「助手」完成本应用各模块的核心任务：了解状态、分析材料、发起操作、调整配置、跟踪执行，并核验实际结果。

助手继续放在「总览」下面，沿用当前流式对话。Jobs、报告、轮次、调度和设置页面提供详情、精细编辑和必要的人工输入；助手结果可以直接跳转到对应对象。涉及密码、API Key 等内容时，可以在助手内通过受保护的输入卡片完成操作。

最终应支持这样的连续操作：

> 查一下近期 Agent 记忆研究缺什么 → 创建跟踪 Job → 每周一上午九点运行 → 看本次执行为什么失败 → 调整后再运行 → 比较最近几次报告 → 把选中的结论加入行动跟踪。

也应支持单独的管理请求，例如「暂停这个周期计划」「切换模型并测试」「查看本月用量」「撤销报告分享链接」。

开发沿用此前已确认的方式：每次接入一个能实际使用的业务闭环，验证后再扩展。阶段按能力划分，不预设天数、成本上限、工具数量或成功率门槛。

## 2. 当前基线与关键差距

### 已具备

- 助手已支持 Jobs 查询、读取配置、创建、局部修改、删除、手动运行、取消手动运行、查看历史。
- 模型文字、工具状态和完成结果通过 SSE 实时传到页面；工具调用参数完整接收和校验后才执行。
- 已复用 Jobs 的权限校验、配置校验、备份、冲突检查、后台执行和审计；当前 provider 已通过实际流式及 Jobs 操作验证。
- 同一浏览器标签页内，切换页面再返回可以接续正在进行的请求；中断时保留已收到的文字和操作结果。

### 扩展时需要处理的具体差距

| 当前事实 | 对后续开发的影响 |
| --- | --- |
| 工具与通用循环集中在 `jobs_assistant.py`，系统提示也限定 Jobs | 接入调度时拆出通用循环和领域工具，保持现有接口、事件和能力兼容 |
| 会话在前端 `sessionStorage` 中保存最近消息；服务端没有会话和操作回执存储 | 刷新、跨设备、服务重启后的恢复不能依赖当前内存 Promise；写操作结果需要可查询 |
| 后续请求主要携带文字和操作摘要，没有服务端管理的对象引用 | 「它」「这个计划」「上次报告」跨领域时容易指错，要保存对象类型和真实标识 |
| 手动 Job 使用 Web 进程中的执行器；周期 Job 使用独立调度执行器 | 查询、日志和取消需要识别运行来源；Web 重启会取消该进程中的手动任务，不能宣称所有运行都跨重启继续 |
| 当前 `cancel_job` 操作 Web 的 `TaskRegistry` | 不能据此宣称已取消独立调度 worker；周期运行需要新增明确的取消入口 |
| 调度 worker 当前将取消事件导致的无报告结果视为失败，失败可能进入重试 | 引入用户取消周期运行时，要区分主动取消与超时，避免取消后又自动重试 |
| 报告问答 API 保留，但未作为助手工具接入；检索默认偏向最新轮，并用历史关键词放宽 | 历史分析需要明确日期、Job、轮次和报告范围，不能仅把整句话交给现有问答接口 |
| 系统配置读取接口包含原始 YAML 与 `parsed`，不仅有脱敏数据 | 助手配置工具需要专用投影，不能直接把管理员配置接口的完整结果放进模型上下文 |
| 普通 LLM 连通性测试只证明能回复短文本 | 切换 provider 时，还需验证助手使用的工具调用与流式组合 |

这些是按当前代码确认的接入问题，不表示要先做一次全站重构。

## 4. 各阶段共同遵循的交互与执行约定

### 4.1 让自然语言落到真实对象

复用现有标识：Job 使用完整相对路径，计划使用 schedule ID，运行使用来源和 run/task ID，报告使用相对路径，轮次使用日期，行动使用 item ID。

助手后台保存最近相关对象的类型与引用。用户说「改成周五」时，先确定指的是哪个计划；「取消这次运行」需要确定运行来源与具体一次执行。没有足够上下文、存在重名或目标不唯一时再询问。

从详情页面增加「在助手中处理」入口时，只传对象引用和用户选中的内容。后端重新读取对象和校验权限，预填内容不自动执行。模型输出的链接不作为对象存在或权限允许的证据。

### 4.2 执行授权与结果反馈

- 用户明确要求的常规操作直接执行；分析、解释、建议请求保持其原意。
- 一次请求可以包含多个明确动作，不为每个内部工具调用重复请求确认。
- 对象、外发目的地或影响范围不清楚时，只补齐缺少的决定。对批量删除、权限变更、公开访问、服务关停等，先把具体对象和影响展示清楚；明确授权已覆盖的步骤不重复询问。
- 报告、日志、任务 prompt 和外部材料是数据，不能自行成为管理应用的指令。
- 流式文字、操作结果卡片和业务状态分别表达：已提交、正在运行、已完成、失败、部分完成、结果待确认。只有得到真实结果才能宣称完成。

若采用确认卡片，卡片绑定具体参数和对象版本。修改参数后重新校验受影响部分；不能用一句「确认」执行模型后来重新生成的一组动作。

### 4.3 断线、多步任务与取消

随第一阶段写操作扩展，补最小的服务端会话、对象引用和操作回执。可以复用本项目的 SQLite 方式，具体表结构在实施时确定；先支持当前对话恢复和结果查询，历史会话管理界面按使用需要再增加。

写动作关联服务端操作标识，保存已知结果和对应业务对象。重复请求先查询已有结果；结果未知时重新读取实际 Job、计划或运行状态，不自动重放整个请求。文件、数据库和外部执行之间存在中断窗口，不能仅增加一个操作表就承诺所有动作恰好执行一次。

「创建 Job → 设置计划 → 运行」中途失败时，展示每一步已知结果，允许从失败处继续。优先复用已有组合能力，例如创建 Job 的 `recurrence` 参数及其失败清理；不重复创建已有对象，也不默认删除已经成功创建、可能已开始使用的对象。

区分三种操作：停止助手当前响应、取消某次研究运行、暂停后续周期。断开助手连接后不再继续发起后续工具操作；已经启动的后台任务按其业务状态管理。

### 4.4 复用应用本身的规则

- 保持现有 viewer/editor/admin 和本人账号范围。调度目前连读取也是 admin 权限，接入助手不会自动改变这一点。
- 工具入口明确检查权限；直接调用路由函数不会自动执行 FastAPI 的依赖校验。
- 接入某个业务域时，按需将重复的核心操作下沉到共享 service，供原页面/API 与助手使用，保留备份、版本冲突、预算、锁和审计。
- 密钥、密码及新 Token 的原值通过受保护输入/结果卡片直达对应后端，不写入模型上下文或普通聊天记录。工具只返回已配置状态及必要的非敏感信息。
- 用量区分模型 token、估算费用和已配置预算；缺少价格时如实显示费用未知，不让模型猜账单。

## 5. 分阶段开发

### 阶段 1：从管理 Job 扩展到管理任务运行

**目标：** 在助手中完成「建任务、设周期、看执行、调整或取消」，形成日常任务管理闭环。

**交付 1A：周期计划，建议作为下一次开发范围。**

1. 将现有循环从 Jobs 工具中拆出，新增调度工具适配；现有 Jobs 行为与 SSE 协议兼容。
2. 接入计划列表/详情、自然语言时间解析、执行预览、创建、修改、暂停、恢复和删除。
3. 计划结果展示目标 Job、时区、频率、接下来三次时间、执行器状态及最近执行结果，并能打开调度详情。
4. 保存最近 Job 与计划引用及写操作回执；刷新后先核验结果，不重新执行请求。
5. 创建并设置周期时复用已有组合入口；已有计划走修改。当前托管实现限制同一 Job 一个计划，沿用该行为并说明冲突，需要多计划时再评估扩展。

时间表达使用可见的时区，支持用户指定 IANA 时区。「暂停计划」保持已有正在运行的任务；「恢复」按现有规则从下一次时间开始。具体执行约定以 [调度说明](scheduling.md) 为准。

当前是五字段 cron。一次性触发、节假日规则、严格按耗时计算的间隔等，不能无损映射时应说明差异，不静默近似；确认实际需求后再扩展调度模型。

旧 cron 和矩阵 launchd 复用现有业务接口管理；新普通计划进入托管调度器。模型使用结构化计划参数，由业务层构造执行方式。

**交付 1B：运行追踪与取消。**

- 汇总手动和周期运行的来源、状态、错误、日志与报告链接，保留原始业务记录的归属。
- 根据明确的一次运行查询和取消。周期 worker 取消需新增后端入口，区分用户主动取消与超时，主动取消不触发失败重试。
- 若实现通过 worker 信号完成取消，后端验证运行记录及进程归属；模型传运行引用，不直接指定系统 PID。
- 调度器在线、计划已保存、任务已启动、报告成功分别判断。运行详情由持久化记录和实际产物核验。

同阶段在具体任务需要时补 Jobs 模板选择、基于模板创建、复制以及 sources 编辑；这些扩展不阻塞 1A 的调度交付。模板库本身的增删改保留在覆盖范围内，随任务配置工具补齐。

**真实验收：**

- 「创建一个跟踪 Agent 记忆的 Job，每周一上午九点，上海时间运行」：实际生成 Job 和计划，预览与调度页一致；刷新后对象仍可定位。
- 「改成周五」「暂停它」「恢复它」：操作同一个计划，未生成重复计划，启停和下次时间正确。
- 在隔离执行器中完成一次实际周期运行，助手查到生成的报告；取消另一条运行后，它不自行重试，后续周期是否继续符合用户请求。
- 断线后查询已创建的计划；重复提交不会又建一份。执行器离线时给出真实失败及已有对象状态。
- viewer/editor 不能借助手获得调度管理员能力。

### 阶段 2：报告分析、消费与研究任务调整

**目标：** 在助手中找到、读懂、比较和管理报告，并将用户选中的分析结论转成下一步研究任务。

**范围：**

- 接入报告列表、按日期/Job/分类等筛选、全文与混合检索、原文读取、相关段落展开。
- 将现有 `core/qa.py` 和检索能力作为可复用能力，支持助手分析中的证据获取；避免为了一个答案再启动一套互不共享上下文的问答助手。
- 历史比较明确实际覆盖的日期、轮次、报告和缺失项；需要时按时间段或轮次分别检索、读取、汇总。返回部分相关片段时，不能宣称已经穷尽全部历史。
- 回答中的引用可以打开具体报告，显示报告日期；区分报告记载、报告之间的差异和助手推断。
- 收藏、标签、已读、评分由用户意图驱动。报告下载/HTML 导出通过结果卡片交付文件或下载链接。
- 把选中的结论变为 Job 草稿或对已有任务的修改，携带来源。用户仅要求分析时不自动创建任务。
- 用于调整研究任务的 sources、模板及必要运行参数采用结构化更新，保留未修改字段。

报告分享、邮件发送与通知在阶段 4 接入，届时明确受众与内容。

**真实验收：**

- 「比较过去一个月这个 Job 的结论变化」：报告范围真实、引用能打开，能说明无报告的时段。
- 同一主题的新旧报告存在冲突时，答案保留冲突及各自日期，不能把旧结论冒充当前事实。
- 「收藏这些报告并打上记忆标签」：报告页同步可见；单纯分析时元数据保持原样。
- 「根据第一个缺口创建一个 Job」：能定位用户选中的结论，创建结果保留证据出处和清晰研究目标。

### 阶段 3：情报轮次与行动闭环

**目标：** 用户在助手中管理整轮情报生产，并持续处理报告产生的行动和观察项。

**范围：**

- 查历史轮次、阶段进度、失败原因、产物质量提示、结构化行动/观察/来源及跨轮 diff。
- 接入整轮运行、已有补跑规则和取消。补跑计划说明涉及的未完成阶段及需要更新的下游结论。
- 当前 `/retry` 处理未完成阶段与下游失效；若要「指定重跑已完成的 P5」，新增阶段级重跑业务能力，再暴露为工具。
- 查行动、测试与观察项，更新完成/放弃/备注，查看跨轮延续及历史决定。
- 用户要求将行动转为研究任务时，复用 Jobs 和调度工具；保持行动来源、任务和轮次之间的关联。

**真实验收：**

- 「今天这一轮哪里失败了，补跑它」：引用正确轮次和日志，补跑范围符合依赖关系，助手能查到新结果。
- 重跑上游后，下游综合报告按业务规则更新；不会展示旧综合结论为本次新产物。
- 「把这条行动标成已完成，备注已测试」：修改指定条目，轮次详情和后续查询一致。
- 模型读到报告中的操作建议时，只作为分析材料；未获用户指令不执行管理动作。

### 阶段 4：全局诊断、配置与内容分发

**目标：** 助手能解释系统为什么没有按预期工作，并在明确授权下完成配置和分发。

**范围：**

- 聚合健康、用量、预算、模型/搜索/Embedding 连通性和调度状态；读取相关且脱敏的错误片段，不默认把全量日志灌入模型。
- 提供非敏感的有效配置视图和结构化 patch。说明配置作用域：当前助手与研究任务共用 `ai` 配置，变更可能影响后续研究运行。
- provider/model 切换先测试候选配置；验证普通调用、工具调用与流式组合。失败时保留可用配置并给出原因；用户需要强制保存时，由明确操作决定。
- 保存配置复用既有版本检查与备份；返回待生效或已生效的真实状态。
- 增加不依赖 LLM 的直接撤回入口：错误配置导致助手无法回复时，仍能通过卡片/设置页恢复先前配置。
- 查看索引覆盖、触发重建和跟踪结果。重建属于后台操作，需要进度、失败项和恢复路径，避免长时间阻塞一条普通回答。
- 接入预算、研究参数、通知和报告清理等现有设置；密钥等使用受保护输入。
- 接入测试通知、指定报告邮件、分享链接创建/列表/撤销。发送前有明确目的地与内容范围；「帮我分析」不隐含外发许可。

**真实验收：**

- 认证失败、模型不支持工具、搜索不可用、调度离线能被区分，诊断依据来自实际测试与状态。
- 切换到可用 provider 后，助手仍能流式调用工具；错误候选不覆盖正常配置，撤回入口不依赖模型恢复。
- 工具上下文、消息、操作回执和日志中不出现用户输入的密钥/密码原值。
- 对选定测试地址或渠道发送的内容与用户要求一致；分享链接可查看有效状态并能撤销。

### 阶段 5：账号、访问与运行维护

**目标：** 完成应用管理能力覆盖，并能处理会改变助手自身可用性的操作。

**范围：**

- 管理员查询/创建/更新/禁用/删除用户、调整角色、强制下线；保留现有防止自我锁出的保护。
- 用户管理自己的会话、API Token 和密码；本人范围由服务端当前身份确定。当前 Token API 不提供细粒度业务 scope，不对用户声称已有这类隔离。
- 密码输入、新 Token 的一次性展示走受保护卡片，普通聊天仅记录操作结果。
- 查应用版本、监听地址、局域网配置及待重启状态；复用现有 gateway 接口，并明确配置保存不等于监听地址已改变。
- 关停/重启前查询受影响的手动运行和当前操作；按用户请求等待或取消，不把中断隐瞒成完成。
- 应用内可靠重启与网关重绑定需要专门的业务操作和状态回执。现有 `shutdown` 依赖 PID 文件，不等于已经具备可恢复重启。
- 自身服务可能中断的操作，在执行前持久化回执和恢复所需引用；恢复后重新核验健康与目标状态。

**真实验收：**

- 管理员完成用户管理，普通用户不能越权；只能撤销自己的 Token/会话。
- 密码和新 Token 不进入 LLM 上下文或历史聊天记录，现有账号页结果保持一致。
- 局域网配置变更后能准确区分保存、待重启、实际生效；不显示尚未可用的访问结果。
- 在隔离服务中完成关停/恢复流程，保护或明确处理既有任务，并在恢复后查询到真实结果。

## 6. 必要实现结构与约束来源

建议沿用「流式对话 → 助手运行时 → 领域工具 → 共享业务服务 → 现有存储/执行器」。这里描述职责，不要求预先建立一个大型框架。

| 部分 | 本次计划中的作用 |
| --- | --- |
| 助手运行时 | 会话、对象引用、工具循环、取消、步骤结果与恢复；不自行实现业务调度 |
| 领域工具 | 结构化参数、必要返回信息、当前用户权限；逐阶段接入 Jobs、调度、报告等 |
| 共享业务服务 | 与原页面/API 共用核心校验、执行、版本检查、备份及审计 |
| 前端结果组件 | 统一展示对象、状态、引用、下载与必要输入；不把一切都转成纯文字 |
| 现有执行与数据 | Jobs YAML、运行记录、调度库、报告库、轮次和跟踪数据继续作为业务事实来源 |

工具增加后可以按领域组织，并根据真实任务表现决定是否选择性加载。先不新增 MCP、外部 Agent 框架、多 Agent 分工或通用插件平台的交付依赖；未来有明确接入需求或验证收益后再选择。

硬约束来源：

- **用户已确认方向：** 助手统一入口、保持渐进开发、当前 Jobs 与流式能力继续可用、最终覆盖应用核心能力。
- **仓库现有约定：** `AGENTS.md` 的共享引擎、LLM API 调用方式、调度执行约定、模型输出不可信、隔离测试等。
- **已核对的工程事实：** 现有权限、手动与周期执行来源、计划唯一性、配置返回形态、已存在的 API 边界。

具体模块名称、存储表结构、阶段细分与实现顺序仍可调整。现有文档中的旧工期、旧测试数量和“已完成全部里程碑”等描述不作为本计划的新验收条件。

## 7. 验证与推进方式

每个交付用一条可体验的端到端任务验收：实际对象和产物正确、流式反馈清楚、失败后可继续处理、专用页面状态一致。测试选择服务于真实问题，不用工具数量或测试数量代替产品验收。

- 业务/API 测试：权限、参数、真实状态、版本冲突、备份、重复请求与部分失败。
- 页面测试：流式增量、操作卡片、对象跳转、刷新恢复、明确对象选择及受保护输入。
- 真实模型测试：在隔离数据上执行完整任务，检查真实写入和引用；覆盖歧义、无结果、断线、模型失败和恶意材料。
- 调度/系统测试：使用隔离 state、临时服务和模拟渠道；按 `AGENTS.md` 与调度说明测试，避免触碰用户真实 cron/LaunchAgent 或对外发送。
- 修改共享 LLM、执行器、检索或调度时，补相应回归；报告事实、环境限制和既有失败，不把未通过的完整检查说成通过。

达到当前交付的业务结果后进入下一项，不扩写无关基础设施。发现技术路径不能达成结果时，记录实际现象与最小验证办法，再调整方案。

**实施记录：** 各阶段已按连续授权推进，实际完成项和验证结果以 [开发进度](assistant-harness-progress.md) 为准。
